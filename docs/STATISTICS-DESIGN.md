# Опциональная статистика и web: проект архитектуры

Русский | [English](STATISTICS-DESIGN.en.md)

Статус: **реализовано в optional Cargo feature `web` версии 0.2.0**.
Инструкция, фактические ограничения и настройки: [STATISTICS.md](STATISTICS.md).
Ниже сохранены исходные проектные требования; измерения и ограничения реализации
имеют приоритет над целевым бюджетом. Базовый образ не содержит HTTP-сервера.

## Цель и размещение

Статистика и web работают в том же локальном контейнере на MikroTik. Все решения
по WAN остаются у существующего Rust/RouterOS механизма; web получает только
снимки для чтения и не становится дополнительным исполнителем маршрутизации.
Остановка web не должна менять SLA, heartbeat, conntrack или выбор WAN.

Базовый образ остаётся `FROM scratch`. Предлагается Cargo feature `web`, чтобы
вариант controller-only сохранял минимальный размер. Даже в web-варианте модуль
выключен по умолчанию: нет listener, потока HTTP, истории или web-токена до
явного включения. Framework, БД, Node.js, CDN и отдельный процесс не нужны.

## Источники и данные

Основной источник — уже прочитанный `sdwanStatusJSON`: RTT/jitter/loss,
готовность WAN, актуальность измерений, выбранный WAN и режим container/fallback.
Полную конфигурацию, API-пароль, intent, recovery journal и backup не передавать
в web. Дополнительные счётчики RX/TX читать только по выбранным WAN и с отдельным
интервалом, без дублирования Netwatch-проб. Неудача чтения счётчиков не мешает
решениям контроллера; неизвестные значения — `null`, а не выдуманный ноль.

В RAM хранить:

- короткий текущий снимок WAN/политик, версию конфигурации и признак stale;
- кольцевую историю измерений и скорости по WAN;
- ограниченное кольцо событий: смена WAN, потеря SLA, fallback, reboot/config reset;
- uptime, число переключений и время недоступности в пределах текущего запуска.

Счётчики трафика не являются расчётным биллингом оператора. При сбросе счётчика,
смене интерфейса или reboot не показывать скачок скорости. На смену boot/config
epoch сбрасывать совместимость временных рядов и отмечать границу события.

## Бюджет RAM

Начальный интервал —10 с, история —360 точек (около часа). Жёсткий максимум —
16 WAN и 600 точек. Строки WAN/profile/policy хранить один раз, в точках — индексы
и числовые значения. Бюджет 64 байта на WAN-точку даёт не более 614400 байт для ряда;
это проектный расчёт, не измеренный RSS реализации.

До 128 событий с ограниченной длиной, фиксированный буфер текущего снимка,
ограниченный JSON-ответ и один HTTP-поток со стеком 128 КиБ. Целевой общий бюджет
модуля —до 2 МиБ; его нужно подтвердить на CHR и физическом ARM. Не выделять память
на количество запросов/клиентов без предела. Переполнение кольца заменяет старые
данные, не увеличивает файл или память. Если модуль не помещается в заданный
бюджет, его запуск отклоняется; решения SD-WAN продолжаются.

## Запись на носитель

| Операция | Записи модуля статистики на MikroTik |
|---|---:|
| Опрос, точки истории, события, графики, HTTP-запросы | 0 |
| Heartbeat и обновление RAM-снимка | 0 |
| Перезапуск/reboot | История теряется; автоматического checkpoint нет |
| Скачать JSON/CSV в браузере | 0; файл сохраняет компьютер пользователя |
| Изменить настройки/секрет модуля | Только явная операция подготовки/установки |

Не создавать SQLite/WAL, append logs, cache, access log, temp-file или периодический
autosave. Ответы формировать из RAM; `Cache-Control: no-store`. Container logging
оставить выключенным, не журналировать каждый HTTP-запрос/пакет. Нельзя обещать
нулевые записи всей RouterOS: конфигурация, backup, запуск контейнера и существующий
intent при изменении решения — отдельные операции за пределами RAM-статистики.
Текущий intent не переписывается при неизменном выборе WAN.

Для долгой истории предпочтительно внешнее чтение метрик или ручная выгрузка,
при этом сам контроллер остаётся локальным. Запись на USB/SSD допускается только
как отдельно включаемый режим с явным каталогом, ограничением размера и пакетным
сохранением. Встроенную flash автоматически не выбирать. Такой режим не входит
в первый RAM-only этап. Производитель рекомендует размещать container volumes
на подключённом накопителе: [Container](https://manual.mikrotik.com/docs/containers/).

## HTTP и интерфейс

Первая версия —только просмотр: состояние WAN, графики RTT/jitter/loss и RX/TX,
история переключений, фактический исполнитель и экспорт. Редактор конфигурации
остаётся в существующем GUI. Чтение статистики не запускает apply/rollback.

Предлагаемые ограниченные GET endpoints:

- `/` —встроенные HTML/CSS/JS без внешних ресурсов;
- `/api/status` —безопасный текущий снимок и age;
- `/api/history?max=120` —ограниченное число точек, без неограниченного диапазона;
- `/api/events?since=...` —ограниченные события текущего boot epoch;
- `/api/export` —потоковая выдача ограниченной RAM-истории клиенту.

POST/PUT/DELETE и неизвестные маршруты отклонять. Максимум заголовков 4 КиБ,
короткий путь/query, ограниченные read/write deadlines, ограниченная частота
опроса. Медленный клиент не должен держать lock контроллера: короткий снимок
через `try_lock`/передачу сообщений, JSON/отправка после освобождения lock.
Ошибка bind/клиента/экспорта изолирована от основного цикла.

## Доступ и конфигурация

Доступ разрешается только из явно заданных сетей управления через firewall.
Подготовка по умолчанию продолжает блокировать forwarding к контейнеру. Новые
разрешения появятся только при включении web; DNAT/доступ с WAN не создаётся.
Требуется отдельный случайный read-only web-токен в secret mount, без повторного
использования API-пароля. Токен не передаётся в URL и не сохраняется в конфигурации
JSON или логах. В браузере —в памяти сеанса, не в localStorage.

Для удалённого доступа нужен защищённый канал управления. В первом варианте
маленький HTTP-сервис допускается только внутри доверенной сети/VPN; публичный
HTTPS endpoint, встроенный TLS и изменение конфигурации требуют отдельного этапа.
Нужны same-origin, отсутствие wildcard CORS, запрет framing и безопасная вставка
подписей через `textContent`, без выполнения строк из конфигурации как HTML/JS.

Первоначально предложенный контракт `container.telemetry`: `enabled=false`, `sample_seconds=10`,
`history_points=360`, `port=8080`, явный `allowed_sources`. На этапе этого проекта
поля ещё не принимались валидатором; сейчас реализованная схема описана в
[STATISTICS.md](STATISTICS.md). Путь хранения истории
по умолчанию отсутствует. GUI должен показывать: «История в RAM, после reboot
очистится», рассчитанный размер буфера и разрешённые сети.

## Условия приёмки перед реализацией/включением

1. Выключенный модуль: нет listener/новых правил/выделения истории/дисковых записей.
2. Включённый: bounded history/events/ответы, отказ лишним запросам, нет утечки
   API-пароля/секретов в JSON, HTML, URL, ошибках и stdout.
3. Серия HTTP-запросов/медленный клиент/неверный токен не меняют задержку выбора
   WAN и не мешают native fallback; маршруты/marks/conntrack проверены на CHR.
4. По счётчикам/перехвату I/O нет записи метрик/истории/access logs; unchanged
   intent остаётся без записи. Выгрузка истории создаёт файл только у клиента.
5. Измерены RSS/CPU/размер для трёх архитектур при feature off/on; длительный soak,
   смена конфигурации, reboot, сброс counters и аварийная остановка.

Планируемый порядок: RAM storage и unit limits →санитизированный API →встроенная
страница →LAN/token/firewall GUI →fault/ресурсная приёмка. Публичный порт и
периодическое сохранение на flash не являются частью этого плана.
