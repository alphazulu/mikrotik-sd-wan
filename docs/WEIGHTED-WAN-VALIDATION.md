# Проверка WAN-политик с весами

Русский | [English](WEIGHTED-WAN-VALIDATION.en.md)

Опциональные [политики с весами](WEIGHTED-WAN.md) прошли ограниченные проверки ниже
на RouterOS **7.24.5**. Рабочий роутер не опрашивался. Это отдельный этап, который
не наследует исходную 48-часовую приёмку и 150 измерений v0.3.0.

## Функциональные данные

| Проверка | Результат и область |
|---|---|
| SDK / внешние инструменты / GUI | 414 / 88 unit-тестов; 7 проверок редактора весов на настоящих Tk-виджетах |
| Функции RSC | По 40 случаев на x86 L6 и свежем CHR: все 25 подмножеств 2–4 участников, 10 неверных политик, 5 защитных/lifecycle-проверок допуска |
| Два активных WAN, `3:1:0` | 400 TCP-ответов: 294/106/0; 160 UDP-ответов: 120/40/0 |
| Три активных WAN, `3:2:1` | 120 TCP-ответов: 61/39/20; 120 UDP-ответов: 57/41/22 |
| Отказ WAN1 в этом пуле | Оставшееся подмножество `2:1`: TCP 0/61/19, UDP 0/58/22; все 160 ответов получены |
| Изменение доступности | Отказ/возврат основного и второго WAN; точные исключённые marks удалены, ID и кортежи здоровых TCP/UDP сохранены, счётчики ответов растут |
| Drain / резерв / закрытие | Новые потоки уходят с draining-канала, допустимые сессии сохраняются до срока; работает резерв с нулевым весом; отказ всех SLA закрывает допуск |
| Политики | IP источника И Address List назначения; Address List источника И IP назначения; живое изменение списков, default для исключённого клиента и отдельная закреплённая политика |
| Закрепление | Для `both-addresses` и `src-address` по 80 новых TCP/UDP-соединений оставались на одном WAN при неизменном пуле |

| DHCP | Настоящая потеря аренды и получение другого адреса: проверены новые потоки, source pin и сохранение здоровых сессий WAN2 |

Четыре участника проверялись как функции и схемы правил, а не четыре реальных WAN.
Полные проверки трафика шли на виртуальном x86 L6 с тремя WAN-пирами; проверки CHR
охватывают функции и откат. Код транспорта VPN/LTE сохранён; этот этап не повторяет
полную матрицу протоколов и приёмку физических модемов.

## Ограниченный замер ресурсов

Один кандидат, native-режим, **1 vCPU / 1024 MiB / virtio**, четыре политики.
Default-политика попеременно использовала обычный порядок либо веса `3:1:0`.
Ей соответствовали все 128 адресов генератора; веса только политики client101
не нагрузили бы нужный путь. Порядок A–B–B–A, 10 секунд прогрева и 30 измерения.
В каждом окне завершились все **40 000** новых соединений, включая прогрев;
счётчики клиента/сервера совпали, ошибок обмена нет. Резервации кортежей и портов
назначения не пересекались. Системные настройки TIME_WAIT не менялись.

| Окно | Default-политика | Средний CPU RouterOS | Наблюдаемый CPS |
|---|---|---:|---:|
| 1 | По порядку | 79,07% | 1000,03 |
| 2 | С весами | 85,37% | 1000,03 |
| 3 | С весами | 84,23% | 1000,00 |
| 4 | По порядку | 79,17% | 1000,00 |

Средние: **79,12% по порядку, 84,80% с весами**, наблюдаемые накладные расходы —
**5,68 процентного пункта**. Парные разности — 6,30 и 5,07 пункта. В каждом окне
30 ресурсных и 29 актуальных статусных снимков; первый WAN, состав пула и
закреплённая политика оставались неизменны. Счётчики получателя, средние CPU и
снимки состояния пересчитаны независимо. Две пары не дают доверительного интервала,
максимальной ёмкости, сравнения с иначе инструментированными окнами прежней
оптимизации или аппаратных рекомендаций. В одном окне p95 CPU с весами достиг 97%;
по одному среднему нельзя предполагать запас другого устройства.

Отдельный сопоставимый A–B–B–A-прогон проверил общий механизм допуска при
**обычных политиках в обоих вариантах**: прежний main `e1b612d` против нового
RAM-допуска. Средние CPU окон — 78,93 / 76,97 / 79,55 / 76,90%; средние вариантов —
77,92% старый и 78,26% новый, наблюдаемая разность 0,34 пункта. Парные разности
разнонаправлены (−1,97 и +2,65 пункта); две пары не доказывают эквивалентность или
ускорение. В каждом окне завершились ещё 40 000 новых обменов клиента/сервера
без ошибок. Этот контроль отделён и от PCC-сравнения выше, и от исторической
оптимизации цикла. Сырые счётчики, хеши реально исполняемого контроллера, снимки
состояния, средние CPU, неизменность базовых образов и очистка проверены независимо.

Минимум свободной памяти и прирост логических секторов записи приведены в данных.
Это выборочные показатели всего роутера. Они не выделяют память PCC, не измеряют
циклы стирания NAND и не доказывают нулевую запись на flash. Сам допуск динамический
и после перезагрузки воссоздаётся по свежему SLA.

## Наблюдения и сохранённые ошибки

`selected` и enabled/active флаги API отражают конфигурацию. В исходной DHCP-диагностике
первый основной путь наблюдался около 0,98 секунды; отдельная проба RAM-допуска
ещё показала прежний WAN в двух потоках, первый нужный — около 0,12 с. В новых
ограниченных recovery-проверках все 30 потоков шли через основной уже с первых
наблюдений: примерно 0,085 и 0,090 с. Это не гарантия атомарного переключения.

Неуспешные прогоны сохранены как неуспешные. Среди причин — синтаксис функции,
строковый вместо числового именованный аргумент, гонка чтения пустого результата
в RAM, позднее чтение буфера захвата, потери захвата в ядре, неверный параметр
остановки контейнера, проверка приоритетов пересекающихся политик и повторное имя
журнала. Успешные части этих прогонов независимо перечитаны и использованы повторно;
успешные нагрузочные окна ради удобного отчёта не повторялись.

Два существенных ограничения сохранены: явная смена типа WAN сбросила общий прогрев
SLA и прервала сессии; один цикл опроса web (3 из 30 запросов) истёк по тайм-ауту
во время защищённого изменения селекторов. Runtime-обновление DHCP и стабильный
web после применения затем проверены отдельно. Реальная регрессия удаления оставляла
RAM-записи; исправление явно удаляет только комментарии допуска перед прежней
очисткой статических списков. Чужие dynamic-записи сохраняются. Отсутствующее поле
`disabled` у нового объекта отличали от явного `false` настоящими getter-вызовами,
не игнорируя изменение истинного флага.

Освобождены все собственные процессы, пространства имён, порты и блокировки;
оба базовых x86-образа и исходный CHR не изменились. Экспорты, учётные данные,
лицензионные образы и приватные трассы не публикуются.

## Воспроизведение

- SDK: `python3 -m unittest discover -s tests -p 'test_*.py'`. Unit-тесты внешних
  инструментов запускаются из `labtools/`, настоящие Tk-проверки —
  `python3 tests/gui_balance_smoke.py` (Xvfb на Linux без дисплея).
- На одноразовый RouterOS без политики `nativebalancetest` загрузите канонический
  `native/sdwan-admission.rsc`, [native_balance_cases.rsc](../tests/native_balance_cases.rsc)
  и [JSON случаев](../tests/native_balance_cases.json), сохранив имена файлов.
  Импортируйте проверочный скрипт из временного самоотключающегося планировщика
  с `read,write,policy,test,sensitive`; прочитайте `sdwanBalanceSelfTestJSON` из
  `/system/script/environment`. Требуются `pass=true`, `checks=40`; затем удалите
  временные файлы/задания. Это не проверка реального трафика.
- Матрица трафика/ресурсов использовала существующий
  [адаптер собственного DUT](../labtools/DUT-ADAPTER.md), изолированных пиров,
  настоящие echo-концы и приватный оркестратор. Примитивы и native-случаи публичны;
  весь описанный прогон не представлен одной публичной командой.

Ни прежний длительный прогон, ни эти короткие тесты не являются приёмкой физического
ARM/ARM64, настоящего LTE-модема, максимума 1024 правил или будущей функциональности.
