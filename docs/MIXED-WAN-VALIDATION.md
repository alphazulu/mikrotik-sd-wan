# Смешанная схема WAN, LTE, VPN и OSPF

Русский | [English](MIXED-WAN-VALIDATION.en.md)

**Ограниченная функциональная проверка подтверждена.** Штатные перезапуски
прошли; последующая проверка аварийного снятия питания приведена отдельно ниже.

Стенд: RouterOS 7.24.5, отдельная x86 L6 с 1 vCPU/1024 MiB и CHR-сосед.
Рабочий маршрутизатор и его экспорт исключены. Контроллер работает в RouterOS
либо в локальном Rust scratch-контейнере; хост только создаёт отказы и наблюдает.

## Топология и проверенные сценарии

WAN1 — статический Ethernet. WAN2 — настоящий USB RNDIS, видимый как `lte1`;
его динамический DHCP-клиент настраивается через APN, аренда на стенде — 60 секунд.
VPN1 — существующий WireGuard-выход с транспортами WAN1/LTE. Политика по IP
источника и Address List назначения предпочитает VPN, затем физические WAN.
Отдельно заданы общая политика и клиент, закреплённый за LTE.

Филиал доступен через два WireGuard/OSPF-пути со стоимостью 10/20.
Для филиального трафика проверяются отсутствие маркировки/NAT, соседство Full,
активный OSPF-маршрут и настоящий TCP/UDP-обмен. Одного соседства недостаточно.

| Сценарий | Подтверждённое поведение RSC и контейнера |
| --- | --- |
| VPN остаётся подключённым, но ресурсы за ним недоступны | Политика переходит на следующий WAN; шесть незатронутых потоков сохраняются |
| Основной WAN теряет передачу данных | Общая политика и транспорт VPN используют LTE; филиал использует резервный OSPF-путь |
| Ожидаемое тело HTTP-пробы VPN изменено во время отказа | Пересчитываются затронутые SLA/соединения; исправные LTE/филиальные потоки сохраняются |
| Эквивалентная запись IP источника | Незатронутые SLA и восемь потоков сохраняются |
| Филиальный префикс также включён в VPN Address List | Исключение локальных сетей сохраняет частный маршрут без NAT |
| Оба физических транспорта потеряны | Допуск клиентского интернета закрыт, новая сессия управления доступна; LTE может восстановиться первым |
| Потеря только интернет-SLA при работающих физических путях | Шесть новых TCP/UDP-подключений блокируются без утечки интернет-пакетов; OSPF, филиал и управление продолжают работать |
| Остановка и повторный запуск локального контейнера | Нативный fallback и возврат контейнера сохраняют восемь потоков |

В состоянии адаптера `backend=container` сохраняется и при fallback. Активное
управление контейнером показывает `container.active=true`; при нативном fallback
это `false`, а срок аренды управления истёк.

## Перезапуски и исправление эмулятора

Прошли 16 проверок: четыре штатных перезапуска гостя, по два для RSC и локального
контейнера. Для каждого режима проверены отсутствие основного WAN и одновременная
недоступность основного WAN и ресурсов VPN. После каждого запуска требовались
свежие измерения LTE, настоящий обмен по восьми TCP/UDP-путям и лицензия L6.

Затем в каждом режиме выполнено 125 наблюдений за 125 секунд при аренде DHCP
60 секунд. Все наблюдения сохранили привязанную аренду и ожидаемый выбор WAN;
восемь соединений продолжали обмен без разрыва TCP. Независимо сверены 48
соответствий потоков пакетам и 3616 наблюдений записей conntrack. Сохранение
соединений через саму перезагрузку не заявляется: после неё создаются новые.
Исходники, три родительских диска и очистка ресурсов проверены независимо.

В исходном эмуляторе отменённые USB-запросы удалялись без завершения.
[Протокол usbredir](https://github.com/SPICEorg/usbredir/blob/master/usb-redirection-protocol.txt)
требует ответ с прежним ID. QEMU сохраняет ID отменённых запросов до получения
ответа; при повторном использовании ID мог теряться входящий обмен.

Диагностика RouterOS и USB показала остановку новых запросов чтения после
перезапуска: очередь входящих кадров росла, DHCP-сервер отвечал, но сниффер
RouterOS видел только исходящие запросы. Исправление завершает отменённое
отложенное чтение статусом `cancelled`, сохраняя остальные запросы. Уже
завершённая операция не получает второй ответ.

Набор эмулятора содержит 32 теста, включая 64-битные ID, повторное использование,
независимые запросы и AT endpoint; один TAP-тест намеренно пропускается без
специально подготовленного интерфейса. Старая обработка не проходит три новые
регрессии. Отдельное исправление нулевого хвоста RNDIS не включено в этот результат.

## Исходники и достоверность

Функциональные сценарии используют дерево `317bfeb5c40ceac385219ccab0a1667e11494c36`.
Исправление отмены испытано на дереве `664d737969dcf661ea792aa8de3a88532ea65b3d`
([коммит](https://github.com/alphazulu/mikrotik-sd-wan/commit/fc004a09ee3adb7a604bbd1f91236d11d512ba58)).
Между ними меняются только USB-эмулятор, его тесты и документация.
RSC, SDK, Rust и JavaScript идентичны; шесть образов контейнера не меняются.

Доказательства включают настоящие TCP/UDP-ответы, полные исходные/ответные
кортежи conntrack, маркировки и растущие счётчики; наблюдение исправных потоков
выполняется каждые 0,5 секунды. Внутренний ID conntrack может использоваться
повторно: удаление проверяется по отсутствию прежней маркировки политика/WAN,
а новый маршрут — по NAT и пакетным захватам с нулём потерь захвата.
Один неуспешный снимок API исключён из приёмки соответствующей сцены; её
отдельный повтор прошёл без ошибки наблюдателя. Это ограниченное наблюдение,
не доказательство отсутствия переходов между отсчётами.

Базовые диски, исходники и освобождение ресурсов проверяются независимо.
Сырые журналы, диски и учётные данные остаются закрытыми. CI проверяет оба
профиля Rust, включая `main.rs`, и браузерный код с требованием 100% покрытия
строк и функций юнит-тестами.

## Границы результата

Этот отчёт относится к смешанной функциональности и штатным перезапускам.
Первоначальное ограничение с пустым active при жёстком сбросе устранено и отдельно
проверено в [восстановлении при прерывании питания](POWER-LOSS-VALIDATION.md).
Результаты новой серии не приписываются этому историческому прогону.

Не проверялись физическая LTE-радиосеть, SIM, производительность ARM и соединение
двух сторон за CGNAT без достижимого хаба/ретранслятора. Прежние 48 часов и
150 замеров не повторяются и не приписываются этому изменению.
