# Опциональный выход через существующий VPN

VPN добавляется опционально как обычный WAN (`kind=vpn`). Контроллер работает на самом MikroTik:
RouterOS RSC либо локальный Rust-контейнер с нативным SLA/маршрутизацией.
VPN — ещё один канал того же SD-WAN, с теми же окнами отказа/восстановления,
приоритетами, drain и очисткой conntrack. Отдельного контроллера нет.

Это документация текущей ветки разработки. Полная приёмка, контейнерная
проверка и длительный soak ещё не завершены; опубликованный v0.2.0 этой функции
не содержит. План оставшихся проверок: [VPN-EGRESS-PLAN.md](VPN-EGRESS-PLAN.md).

## Настройка в GUI

1. Заранее настройте клиент WireGuard, L2TP, SSTP или OpenVPN в режиме IP.
   Пароли, сертификаты и ключи остаются в этом клиенте MikroTik.
2. Подключитесь по API, получите настройки и создайте конфигурацию физических WAN.
3. В таблице WAN нажмите **Добавить / настроить VPN WAN**. Выберите существующий
   клиент, имя канала и порядок физических WAN для связи с VPN-сервером.
   Добавление канала сохраняет все существующие политики без изменений.
4. При необходимости включите NAT и разрешение выбранных соединений в firewall
   для этого WAN. Эти параметры есть у любого WAN и по умолчанию выключены.
5. Проверьте контрольные цели канала: они должны проверять целевые ресурсы
   **через VPN**, а не только сервер или handshake. Первоначально мастер копирует
   цели первого физического WAN; при редактировании сохраняет прежние цели VPN.
6. Нажмите **Правило по IP / Address List → WAN**. Источник и назначение независимо
   задаются как любой адрес, IPv4/подсеть или Address List MikroTik. Условия
   соединяются И. Укажите SLA, приоритет правила и очередь WAN, например
   VPN1 → VPN2 → WAN1 → WAN2. Дополнительные порты/VLAN доступны в редакторе.
   Общая интернет-политика также может предпочитать VPN.
7. Просмотрите план и выполните защищённую установку. Создание и сохранение JSON
   в GUI сами по себе не меняют настройки роутера.

Приоритет правила задаётся явно: меньшее число рассматривается раньше.
Недоступность всех его WAN закрывает этот маршрут; следующая политика не
служит резервом. Резервы указываются в очереди WAN самого правила.
Изменение селекторов/порядка правил пересоздаёт управляемые исходящие соединения;
это заранее видно в плане. Обычное переключение SLA очищает только затронутые
метки прежнего WAN соответствующей политики.

VPN опционален: не добавляйте `kind=vpn`, если он не нужен. Отдельного переключателя
или слоя политик нет. Для обслуживания используйте общий `admin_state=drain/down`.
Чтобы убрать канал из проекта, сначала удалите ссылки на него из очередей политик,
затем удалите WAN. Настройки самого клиента сохраняются. Принятые автоматические
маршруты остаются подавленными до явного отката к базовой конфигурации.

Мастер физических WAN сохраняет ранее добавленные VPN и все политики при
включённом сохранении существующих политик и VPN WAN. Динамические адреса не
превращаются в локальные подсети или статические снимки lease. Если общая политика
уже предпочитает VPN, её очередь также сохраняется. Исключение необходимого
политике физического WAN отклоняется с объяснением.

## Файл конфигурации

Дополнение к обычному JSON (имена WAN/профиля должны существовать):

```json
{
  "wans": [{
    "name": "vpn1",
    "kind": "vpn",
    "interface": "sstp-existing",
    "vpn_type": "sstp",
    "vpn_endpoint": "exit.example.test",
    "underlays": ["wan1", "wan2"],
    "masquerade": false,
    "allow_selected_forward": false,
    "probe_table": "sdwan-probe-vpn1",
    "icmp_target": "203.0.113.10",
    "probes": [
      {"name": "a", "type": "https-get", "host": "203.0.113.10", "port": 443},
      {"name": "b", "type": "tcp-conn", "host": "198.51.100.10", "port": 443}
    ]
  }],
  "policies": [{
    "name": "vpn-targets",
    "source": "0.0.0.0/0",
    "source_list": "VPN users",
    "destination_list": "VPN destinations",
    "priority": 10,
    "table": "sdwan-vpn-targets",
    "profile": "default",
    "mode": "prefer",
    "wans": ["vpn1", "wan1", "wan2"],
    "allow_degraded": false
  }]
}
```

Это фрагмент, а не самостоятельная конфигурация. Добавьте его объекты к
физическим WAN и общей политике. Для L2TP/OpenVPN задайте `vpn_type` как
`l2tp`/`openvpn`. Для WireGuard дополнительно требуются публичный ключ exit-peer
`vpn_peer_public_key` и уникальный локальный UDP-порт `vpn_listen_port`.
У WireGuard должен быть ровно один включённый peer с `0.0.0.0/0` в allowed-address;
филиальный peer с частными подсетями нельзя использовать как Internet exit.

Адрес/шлюз VPN не сохраняются в JSON: RouterOS определяет их по текущей сессии.
Каждый VPN ссылается только на физические underlay WAN; циклическая зависимость
или использование VPN как underlay филиального overlay запрещены.

Старые файлы с `vpn_egress` читаются для совместимости. При сохранении через GUI
или создании пакета SDK переносит NAT/firewall-флаги на VPN WAN и удаляет этот
устаревший блок. Явные флаги WAN имеют приоритет. Новый файл содержит только
обычные `wans` и `policies`.

## Работа и границы

Новые соединения выбираются через нативные `src-address-list` и
`dst-address-list`; отдельные IP/подсети можно сочетать со списком другой стороны.
Селекторы находятся на `jump` в общую цепочку конкретной политики; маркировка и
закрывающий маршрут находятся внутри этой цепочки. Статические,
DNS и временные записи остаются собственностью существующего Address List.
Контроллер не копирует и не обновляет его состав в цикле SLA. Пустой список
не перехватывает соединения. RouterOS публикует изменения списка в dataplane
асинхронно; тест учитывает короткую сходимость после изменения состава.

Изменение состава влияет на новые соединения. Установленные соединения сохраняют
метку до штатного завершения либо переключения политики. При отказе/возврате
очищаются только conntrack-метки прежнего канала соответствующей политики.

Внешний транспорт закреплён за физическим WAN. Для WireGuard используется
уникальный локальный UDP-порт; для PPP — реальный endpoint/протокол. Служебное
правило PPP находится после классификации контрольных проб, чтобы пробы другого
WAN не ушли через выбранный underlay. L2TP учитывает динамические UDP-порты и
IPsec ESP/NAT-T. Смена физического пути переподключает включённый PPP-клиент.

При принятии PPP сохраняется исходный `add-default-route`; OpenVPN также
переводится в `route-nopull=yes`, чтобы серверные маршруты не обходили SLA.
API и native installer блокируют не принятые динамические OpenVPN def1 routes
(`0.0.0.0/1`, `128.0.0.0/1`); маршруты других протоколов этим исключением не
принимаются. Исходные опции восстанавливает явный откат к базовой конфигурации с проверкой
идентичности клиента и отсутствия посторонних изменений. При удалении канала
из SD-WAN автоматические маршруты остаются подавленными до такого отката.
Существующие настройки аутентификации не меняются.

Текущая реализация рассчитана на IPv4 и клиентов в обычной таблице main.
Одинаковые локальные IPv4 на разных каналах требуют VRF и пока не поддерживаются:
контрольные пробы должны отказать закрыто, а не выйти через другой канал.
На L2TP перед добавлением требуется `allow-fast-path=no`: FastPath обходит
маркировку, firewall и connection tracking. Мастер и локальный валидатор отклоняют
клиент с включённым FastPath, не меняя эту настройку автоматически. См.
[официальное описание FastPath](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/packet-flow-in-routeros/).
Прямой SSTP поддерживается; HTTP proxy отклоняется с явной ошибкой. Клиенты с VRF и начальная DNS-загрузка endpoint при полностью закрытом
main требуют отдельных приёмочных проверок; поддержка этих схем не заявлена.

На CHR 7.24.5 проверена смена A-записи существующего WireGuard endpoint:
RouterOS обновил DNS Address List и текущий адрес peer, общий контроллер обновил
служебный маршрут и подтвердил доступность ресурса. Имя в настройках клиента
не переписывалось. Это не задаёт универсального времени обновления DNS;
оно зависит от TTL, резолвера и поведения клиента. Документация
[WireGuard](https://manual.mikrotik.com/docs/cli-reference/interface/wireguard/peers/)
допускает hostname, но не обещает фиксированный срок его обновления.

Живые состояния и транспортные подписи хранятся в RAM. В штатном цикле нет
записи статистики на носитель. Address List выгружается ограниченным снимком
только для выбора имени в мастере или явного объяснения соединения. Автоматическое
обновление диагностики его состав не выгружает. При превышении бюджета снимка
диагностика сообщает неизвестный состав, не предполагает совпадение со всем.

## Документация RouterOS

Семантика существующих клиентов и параметров проверяется по официальным
[WireGuard](https://manual.mikrotik.com/docs/virtual-private-networks/wireguard/),
[L2TP](https://manual.mikrotik.com/docs/virtual-private-networks/l2tp/),
[SSTP](https://help.mikrotik.com/docs/spaces/ROS/pages/2031645/SSTP),
[OpenVPN client](https://manual.mikrotik.com/docs/cli-reference/interface/ovpn-client/).
Текущая online CLI-справка описывает более новую версию; фактическая приёмка
этой ветки выполняется на CHR **7.24.5**.

Проверенные сценарии и оставшиеся ограничения: [VPN-EGRESS-VALIDATION.md](VPN-EGRESS-VALIDATION.md).
