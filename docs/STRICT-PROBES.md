# Строгие HTTP-проверки

Русский | [English](STRICT-PROBES.en.md)

Проверяйте точное тело ответа или определённый путь, когда открытого TCP-порта
недостаточно для подтверждения доступа через WAN к нужному сервису. Эти проверки
участвуют в существующем кворуме и выборе WAN по SLA, включая VPN-каналы.

Фрагмент показывает нужные поля; это не полная конфигурация:

```json
{
  "health": {
    "strict_probe_interval_seconds": 10,
    "strict_probe_timeout_ms": 2000
  },
  "probe": {
    "name": "service",
    "type": "https-get",
    "host": "service.example.com",
    "port": 443,
    "http_path": "/health",
    "http_codes": [200],
    "http_expected_body": "healthy\n"
  }
}
```

Поместите пробу в массив `probes` нужного WAN. Тело сравнивается точно, включая
перевод строки. Ограничение тела — 1024 байта UTF-8. HTTPS проверяет сертификат;
перенаправления не выполняются. Для проверки тела или пути ожидаемые коды должны
быть 2xx. Обычная HTTP-проба Netwatch может ожидать и другие HTTP-коды.
Путь должен начинаться с одного `/` и содержать не более 256 символов.

Ожидание тела, включая пустую строку, или путь, отличный от `/`, включает
асинхронную загрузку RouterOS fetch. Netwatch проверяет TCP-доступность;
одного открытого порта недостаточно для успешной строгой проверки. Worker
использует текущий исходный адрес WAN. Результат также связан с поколением,
точной сигнатурой пробы, шлюзом, ID Netwatch и токеном слота. Ответ старого
задания, адреса, объекта пробы или конфигурации не подтверждает новую проверку.

## Планирование и ограничения

В обоих режимах контроллера используются два общих слота HTTP-проверок.
Диспетчер запускается раз в секунду, освобождает завершённый слот на следующем
тике и перед повторным использованием отменяет старые worker/timer-задания.
Незавершённый запрос сохраняет свой таймаут; просроченный получает отказ.
Результаты хранятся в RAM. Диспетчер и контроллер отклоняют перекрывающиеся
запуски своих скриптов, учитывая представление задания по имени и по внутреннему
ID, наблюдавшиеся на RouterOS 7.24.5.

`strict_probe_interval_seconds`: 5–300 секунд, по умолчанию 10.
`strict_probe_timeout_ms`: 100–2000 миллисекунд, по умолчанию 2000.
Допускается не более 16 строгих HTTP-проб суммарно на всех WAN. Проверка
конфигурации также требует:

```text
ceil(число_строгих_проб / 2) * (ceil(таймаут_мс / 1000) + 1) <= 2 * интервал_с
```

При таймауте 2000 мс 12 проб укладываются в стандартный интервал, 13 — уже нет.
Для 16 нужен интервал минимум 12 секунд. Это ограничение при приёме конфигурации,
а не гарантия задержек планировщика на любом устройстве. Нагрузку CPU, частый
опрос API и медленные цели нужно проверять на выбранной платформе.
Не дублируйте цели для увеличения кворума: host/type/port должны различаться.

Результат старше `2 * интервал_с + 3` секунд отклоняется. Раннее освобождение слота
этот предел не меняет. Ошибочный или устаревший результат не становится UP из-за
одной лишь доступности TCP-порта.

## Повторение ограниченной проверки диспетчера

Нужен отдельный CHR 7.24.5 с пустыми scripts/scheduler/Netwatch и именем
`sdwan-strict-contract`. API доступен только через перенаправление на loopback.
Тест импортирует функции, создаёт управляемые задания и отключённые объекты
Netwatch. После теста удалите эту VM; запуск на уже установленном SD-WAN для
проверки развёртывания не предназначен.

```sh
python3 tests/strict_dispatch_acceptance.py \
  --api-url api://127.0.0.1:37474 \
  --credentials /path/to/private-credentials.json \
  --output /path/to/private-result.json
```

Формат учётных данных: `{"username":"admin","password":"YOUR_LAB_PASSWORD"}`.
Учётные данные и исходные результаты храните вне публичного дерева.

26 проверок выполняют настоящий RSC: владение завершёнными и незавершёнными
слотами, поздние таймеры, все ограничения личности callback, смену ID Netwatch,
отказ по просрочке, отмену точных имён заданий, предел двух слотов, перекрытие
диспетчеров и фактическую защиту входа основного контроллера. Этот запускатель
и сравнение исходной/исправленной библиотеки прошли на CHR 7.24.5. Старая
библиотека провалила проверку раннего освобождения слота.
Эти результаты не подтверждают свежесть проб на шести WAN, все сценарии
переключения VPN, производительность оборудования или 48-часовой прогон.
