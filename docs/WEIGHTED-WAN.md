# WAN-политики с весами

Русский | [English](WEIGHTED-WAN.en.md)

Опциональное расширение использует существующие WAN, SLA и маркировку соединений.
Оно прошло отдельные ограниченные лабораторные проверки. Прежние 48 часов и
сравнение CPU native-контроллера относятся к другой версии. См.
[область проверки и стоимость по ресурсам](WEIGHTED-WAN-VALIDATION.md).

## Конфигурация

Добавьте `balance` в политику `mode="prefer"` или включите **Балансировка** в
её GUI-редакторе. Без поля сохраняется обычный выбор WAN по порядку с failover.
`strict` по-прежнему допускает один WAN и не поддерживает балансировку.

```json
{
  "name": "office",
  "source": "192.0.2.0/24",
  "table": "sdwan-office",
  "profile": "default",
  "mode": "prefer",
  "wans": ["wan1", "wan2", "wan3"],
  "allow_degraded": false,
  "balance": {
    "weights": {"wan1": 3, "wan2": 1, "wan3": 0},
    "classifier": "both-addresses-and-ports"
  }
}
```

Это фрагмент одной политики, а не полная конфигурация устройства. Имена WAN уже
должны существовать в конфигурации. Источник/назначение в виде IP/подсети или
существующего Address List MikroTik, включая их пересечение, остаются селекторами
той же политики. Явный приоритет и порядок общей политики не меняются.
Настроенные VPN-клиенты тоже могут участвовать как WAN; сохраняются требования
к их underlay и SLA.

Вес задаёт ожидаемую **долю новых соединений**, а не скорость, пакеты или точную
пропорцию для маленькой выборки. Одно скачивание идёт через один WAN. Веса не
объединяют провайдеров в одно быстрое TCP-соединение и не переносят NAT-адрес сессии.
Нулевой вес означает резерв по порядку; такие WAN идут после всех положительных
весов. Здоровый резерв используется, когда нет здоровых участников с положительным
весом. Даже при разрешённом degraded fallback здоровый резерв предпочтительнее
участников с нарушенным SLA.

## Закрепление трафика

| `classifier` | Поля хеша | Поведение при неизменном активном пуле |
|---|---|---|
| `both-addresses-and-ports` (по умолчанию) | IP и порты источника/назначения | Соединения одного клиента могут попадать на разные WAN |
| `both-addresses` | IP источника/назначения | Пара клиент/назначение закрепляется за одним WAN |
| `src-address` | IP источника | Один клиент закрепляется за одним WAN |

Хеш выбирает среди доступных участников. При изменении пула WAN для **новых**
соединений может измениться. Уже маркированные здоровые соединения сохраняют WAN
при возврате участника. Приложениям, которым нужен постоянный публичный IP между
несколькими соединениями, подходит закрепление по адресам либо обычная политика
с одним предпочтительным WAN. PCC не поддерживается с прокси/captive portal Hotspot.

## SLA, drain и conntrack

Новые соединения получают только административно включённые участники с актуальным
SLA. Сначала используются здоровые WAN. Degraded допускаются, только если здоровых
нет и включён `allow_degraded`. Recovering, down, устаревшие измерения и
неразрешённые адреса/сессии не допускаются. Сохраняются окна восстановления и hold-down.

При отказе участника контроллер закрывает его допуск и удаляет точные connection
marks этой политики на исключённом WAN. Здоровые участники и другие политики
сохраняют сессии. Восстановленный участник принимает новые соединения без удаления
здоровых сессий на резервном WAN. Drain закрывает новые соединения и сохраняет
допустимые установленные до срока; emergency down или потеря SLA удаляют их.
Если допустимых путей нет, политика закрывается. Удаление conntrack не отправляет
TCP RST и не переносит TCP прозрачно.

`selected` остаётся **первым WAN по приоритету** для маршрута политики и исходящего
трафика самого роутера через default. Балансируемый транзит использует таблицу WAN
каждого соединения. Статус RouterOS дополнительно содержит
`policies.<name>.active_wans` и `balance_mask`. Существующий веб-интерфейс показывает
в `selected` первый WAN, а не весь пул. Исходящие соединения самого роутера PCC
не распределяет.

Явное **изменение конфигурации** WAN, например типа static на DHCP, сбрасывает
общий прогрев SLA и может прервать сессии других WAN. Это отличается от обновления
аренды уже настроенного DHCP WAN. Потеря аренды и возврат с новым адресом
проверяются отдельно на выборочное сохранение соединений. Защищённое применение
конфигурации также может кратковременно прервать опрос опционального web;
проверки стабильного web выполняются отдельно от окна обновления.

## Реализация и ограничения

- От двух до четырёх WAN с положительным весом; дополнительные WAN с нулём служат
  резервом по порядку. Каждому WAN политики нужен один целый вес `0..100`.
- Веса сокращаются на НОД: `30:10` равно `3:1`. Максимум 32 сокращённых слота,
  256 PCC-правил на политику и 1024 суммарно.
- Все непустые подмножества компилируются заранее, максимум 15 групп. При изменении
  SLA группа выбирается одной управляемой динамической записью `0.0.0.0/0` в
  Address List. Правила классификаторов неизменны. Маркированные соединения
  обходят допуск новых соединений.
- Списки/цепочки `sdwan-a-*`, `sdwan-b-*` и комментарии `sdwan:v1:admission:*`
  внутренние. Не добавляйте туда адреса оператора и собственные политики.
- Допуск хранится только в RAM и восстанавливается после перезагрузки по свежему
  SLA. Каждое его изменение не пишет постоянную конфигурацию. Изменения маршрутов
  и журналирование сохраняют обычное поведение RouterOS; это не обещание нулевой
  записи на flash для роутера целиком.
- Native и локальный Rust-контейнер используют общий исполнитель RouterOS.
  Rust передаёт существующий выбор первого WAN; RouterOS сверяет актуальный SLA
  и выбирает подмножество с весами. Внешнего контроллера нет; новый образ контейнера
  для расширения не требуется.

На малых роутерах выбирайте меньше участников и слотов. Ограничения защищают от
неограниченного роста правил и не являются рекомендацией по производительности
железа. Рекомендации требуют измерений на целевой платформе.

Флаги маршрутов/правил API и `selected` подтверждают конфигурацию, а не первый
пакет на новом пути. Переключение проверяется трафиком и захватом пакетов. Исходная
диагностика показала около 0,98 секунды до первого соединения через основной WAN;
пробы RAM-допуска всё ещё показывали около 0,12 секунды. Это не гарантия атомарного
переключения или задержки на физическом устройстве.

Стандартный комплект теперь содержит 12 RSC и JSON, включая
`sdwan-admission.rsc`. Используйте обновлённые GUI/SDK для защищённой установки
и отката; не смешивайте версии файлов. См. [развёртывание](DEPLOYMENT.md).

## Проверка и пример

[Функциональные проверки и четыре ресурсных окна](WEIGHTED-WAN-VALIDATION.md)
включают настоящий TCP/UDP через два/три WAN, failover, drain, селекторы, fallback
контейнера, DHCP, перезагрузку, защищённое обновление и удаление. В том виртуальном
стенде типичный PCC на двух WAN стоил 5,68 пункта CPU при 1000 новых TCP-соединений/с.
[Полный синтетический пример](../config/examples/weighted-wan.json) относится к
топологии лаборатории; для своего устройства создайте конфигурацию мастером.

Официальные источники: [PCC](https://manual.mikrotik.com/docs/high-availability-solutions/load-balancing/per-connection-classifier/)
и [Address Lists](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/firewall/address-lists/).
Текущая документация описывает RouterOS 7.26; реализация также должна пройти
фактические проверки на закреплённой в проекте версии 7.24.5.
