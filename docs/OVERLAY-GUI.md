# Настройка филиалов через GUI

Это необязательная функция разрабатываемой версии. Полная приёмка overlay,
нового контейнера и длительный стендовый прогон ещё продолжаются. Решения
маршрутизации принимает сам MikroTik; GUI нужен для настройки через API.

При CGNAT у обоих филиалов нужен доступный публичный головной узел `hub`.
Каждый филиал `site` устанавливает отдельный исходящий WireGuard-туннель через
каждый WAN. Hub отвечает на эти подключения. Конкретная публичная адресация и
адреса филиалов задаются владельцем сети; в тестах используется только CHR.

1. Подключитесь к нужному роутеру, прочитайте настройки и создайте физические
   WAN обычным мастером. Откройте **Филиалы WG/OSPF** на шаге 3.
2. Явно включите overlay. Укажите роль, уникальный OSPF Router ID, точные
   локальные префиксы для публикации и полный список удалённых сетей. Для hub
   локальный список может быть пустым. Существующий OSPF не мигрируется.
3. Добавьте пути: уникальные имя/локальный UDP-порт, физический WAN, пару
   внутренних адресов /30 или /31, сети за peer и стоимость OSPF. Для site
   задайте доступный endpoint/порт hub и keepalive. На hub эти три поля
   удаляются из итогового JSON: он работает как responder.
4. Нажмите **Подготовить локальные ключи на MikroTik**. Достаточно заполнить
   имена и порты путей плюс общий MTU. Эта отдельная операция создаёт только
   выключенные интерфейсы с ключами, сгенерированными RouterOS. Адреса, peer,
   маршруты и firewall появятся при защищённой установке. Существующий ключ
   сохраняется; коллизии с посторонними интерфейсами и pending-транзакции
   блокируют подготовку.
5. Экспортируйте публичные ключи в JSON. На другом узле выберите строку пути,
   нажмите **Ключ peer из файла**, откройте этот файл и выберите соответствующий
   удалённый интерфейс. Обмен выполните в обе стороны. Не импортируйте экспорт
   RouterOS или закрытые ключи: формат принимает только публичные поля.
6. При необходимости настройте **SLA туннелей**, MTU и опциональный TCP MSS.
   Нажмите **Создать конфигурацию**, сохраните отдельный JSON для этого узла,
   изучите общий план и используйте защищённую установку. Повторите на остальных
   узлах; распределённой атомарной установки на все роутеры нет.

Имена путей на двух концах могут отличаться: выбирайте peer явно. Не публикуйте
management-сети вместо клиентских. Каждый линк имеет собственные адреса, ключи
и порты. Сети филиалов не должны пересекаться с WAN и сетями туннелей. При
потере всех путей точные удалённые префиксы закрываются blackhole-маршрутом.
Интернет-политики и SLA внешнего VPN-egress настраиваются отдельно в том же
SD-WAN, а приватные сети филиалов обходят интернет-классификаторы.

Файл публичного обмена ограничен 32 КиБ и 16 записями. Пароли, private keys,
сертификаты и учётные данные API в него не входят. Подготовка и установка
выполняются по действию оператора; штатный цикл не пишет состояние на флеш.
Выключение опции в проекте создаёт `overlay.enabled=false`; сетевой демонтаж
происходит при общей защищённой установке, а не при открытии окна.

Проверки текущего этапа: 5 offline и 4 live Windows/Tk сценария, отдельные
2 CHR-проверки подготовки с публичным API readback. Живая диагностика показывает
допуск пути по внутреннему SLA и отдельно реальные соседства Full из API OSPF;
при старении снимка эти сведения помечаются устаревшими. Полная матрица hardening
ещё продолжается. См. [топологию и ограничения](OVERLAY-DESIGN.md)
и [общий план](NEXT-NETWORK-PLAN.md).
