# DNS bootstrap для VPN и филиального overlay

Русский | [English](DNS-BOOTSTRAP.en.md)

Настроенный VPN или филиальный overlay может использовать DNS-имя удалённого
endpoint. Локальный контроллер RouterOS продолжает разрешать его, даже когда
SLA обычного Интернета закрыл основную политику, если хотя бы один объявленный
физический WAN административно включён и имеет пригодный адрес/сессию.

Общий вспомогательный код `native/sdwan-dns.rsc` вызывается существующим циклом
контроллера. Он не создаёт отдельный scheduler, внешний resolver или независимую
политику клиентской маршрутизации. Если endpoints заданы только числовыми адресами,
маршруты DNS bootstrap не нужны.

Модуль читает существующие статические и полученные через DHCP/PPP IPv4 DNS-серверы.
Для настроенного HTTPS DoH endpoint он также учитывает A/CNAME-кэш существующего
resolver с ограниченной длиной цепочки. DNS-серверы, DoH URL, сертификаты и учётные
данные не изменяются. Явные `@vrf` и IPv6 resolver сохраняют маршрутизацию оператора;
этот IPv4-модуль не создаёт и не переносит VRF. Resolver во внутренних/филиальных/
линковых сетях и собственные IPv4 роутера используют обычную локальную маршрутизацию.
Другие upstream-серверы пользовательских forwarder требуют своих маршрутов:
модуль не обнаруживает и не переписывает произвольные правила forwarder.

Не более 32 внешних IPv4-назначений получают собственные низкоприоритетные `/32`
маршруты в `main`, distance 250. Правила output закрепляют UDP/TCP 53 обычного DNS
и настроенный TCP-порт DoH за готовым физическим WAN. Пробы с заданным source,
входящие ответы и транспортные правила PPP имеют приоритет. Узкое собственное
source NAT учитывает сокет resolver, сохранивший прежний локальный source.
Предпочтительны здоровые физические пути; готовый объявленный WAN может обеспечить
bootstrap при неуспешном SLA общих интернет-целей. WAN в drain/down исключены.

Начальный host route необходим: первый lookup RouterOS выполняется до output
mangle и корректировки маршрутизации. Одна routing mark не исправляет DNS-сокет,
для которого в `main` нет начального маршрута. См. официальные
[Packet Flow](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/packet-flow-in-routeros/)
и [DNS](https://manual.mikrotik.com/docs/network-management/dns/).
Исполнение проверено на RouterOS 7.24.5; актуальный manual может описывать новые версии.

Завершающее правило политики отбрасывает совпавшие немаркированные клиентские
пакеты, если ни один классификатор WAN их не допускает. Поэтому host route DNS
bootstrap не открывает закрытую клиентскую политику. Локальные назначения роутера,
multicast протоколов маршрутизации и broadcast служебного трафика обходят
интернет-классификацию до WAN marks: OSPF и DHCP должны работать при отказе Интернета.

Модуль хранит подпись структуры в RAM и сравнивает количество собственных объектов.
Неизменная структура не вызывает записи конфигурации/файлов. Изменение настроек,
адресов/кэша DNS, допуска или родителя согласует только объекты
`sdwan:v1:dns-bootstrap`. Отключение, удаление и защищённый откат удаляют его
маршруты, mangle и NAT. Слишком большой исходный модуль отклоняется до SDK deployment;
разделённые модули укладываются в консервативный лимит 60000 байт file contents,
который проверяет сборщик комплекта.

Проверка CHR `tests/vpn_cold_dns_acceptance.py` удерживает внешние DNS-ответы во
время настоящего холодного запуска, закрывает обычные интернет-пробы, затем
разрешает некэшированный DNS. Проверяются SLA VPN-ресурсов, реальный TCP,
сходимость OSPF, запрет обхода клиентской политики через DNS host route и
восстановление. Все пять plain-DNS проверок прошли. Первое холодное TCP-соединение
заняло 20,388 с при явной тестовой границе 60 с; прежние попытки с границей 20 с
остановились до его завершения. Это измерение CHR, а не гарантия задержки в
рабочей сети и не изменение порога SLA. Пассивная трассировка каждого участка
сохранила повторные SYN и переход в established.

Все шесть DoH-проверок CHR также прошли с DNS-именем и нестандартным HTTPS-портом.
Последние DoH-адреса хранятся в ограниченной RAM до 60 с через короткие разрывы
TTL DNS-кэша; свежие A-данные заменяют их, смена URL очищает. В проверенном DoH
прогоне первый холодный TCP установился за 0,832 с. Самоподписанный тестовый сервер
временно отключает проверку сертификата и возвращает исходное значение;
контроллер этот параметр не меняет.
