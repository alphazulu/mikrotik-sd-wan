# Приёмка контейнера 0.4.0 на hAP ax2

Русский | [English](HAP-AX2-04-VALIDATION.en.md)

13 ноября 2026 опубликованный **ARM64 base-образ 0.4.0** прошёл функциональную
приёмку на отдельно выделенном hAP ax2, модель C52iG-5HaxD2HaxD, RouterOS 7.25.1.
Контроллер выполнялся локально в непривилегированном scratch-контейнере с UID
65532:65532; SLA и резервный контроллер выполнялись на RouterOS.

Пакет container уже был установлен. Это проверка установки из остановленного
подготовленного состояния, а не обновления работающего производственного 0.3.
Для 7.25.1 использовался явный лабораторный opt-in SDK; эта проверка не разрешает
произвольные версии RouterOS. [Контракт и согласованное обновление](RAM-CONTROL.md).

| Проверка | Подтверждённый результат |
|---|---|
| Функциональный прогон | 26 проверок |
| Независимая сверка | 72 уникальных TCP/UDP-потока, девять фаз; echo-ответы, полные conntrack tuples, марки, NAT и оба направления внешнего захвата |
| Политики | Общий выход через WAN1 с резервом WAN2; клиент, закреплённый за WAN2; сочетание IP источника и MikroTik Address List назначения |
| Отказ | Недоступность контрольных ресурсов при поднятом WAN и отключение виртуального интерфейса; переход на резерв и возврат |
| Соединения | Старые WAN1 bindings удалены по полным tuples; незатронутые TCP/UDP через WAN2 сохранены в шести фазах, без переподключения TCP |
| Резервное управление | Остановка контейнера передаёт управление RouterOS; запуск возвращает принятые решения Rust |
| Перезагрузка | Настоящий reboot hAP, новый boot fence и повторные реальные TCP/UDP-ответы |
| Изменение настроек | Приоритет изменён без смены revision; вырос generation, применился новый выбор WAN |
| Восстановление | Реально загружена зашифрованная исходная backup-копия; проверены исходные файлы, десять групп статической конфигурации и остановленный прежний контейнер |
| Очистка | Временные интерфейсы и процессы удалены; журнал владения пространствами имён чистый |

## Стенд и границы

У hAP один физический аплинк. Два виртуальных WAN и LAN доставлялись через
локальные Linux namespaces, VXLAN и WireGuard с компьютера в том же коммутаторе.
Генераторы и серверы отвечали снаружи MikroTik. Загрузка образа также прошла через
внутреннюю сеть стенда с проверкой SHA256 на роутере.

WSL имел MTU 1280; первоначальный вариант виртуальных туннелей с MTU 1370 терял
большие пакеты. Диагностика сохранила успешные маленькие и неуспешные большие
пробы. После изменения только временных интерфейсов на WG MTU 1200 и внутренний
MTU 1140 оба клиента прошли TCP/UDP и DF ping на выбранном MTU. MTU компьютера,
его маршруты и firewall не менялись. Это не измерение максимального path MTU.

WAN здесь виртуальные, с общим физическим транспортом. Результат не подтверждает
два независимых провайдера, LTE radio/SIM, все VPN-протоколы, raw Ethernet capacity
или длительную устойчивость 0.4.0. Первичный прогон выполнен с двумя статическими
WAN. Для него заданы лабораторные SLA: RTT 500 ms, jitter 250 ms, loss 5%.

Первичное [сравнение нагрузки и записи](HAP-AX2-04-PERFORMANCE.md) содержит 19 пригодных интервалов из 27; восемь отрицательных UDP-интервалов сохранены. Предыдущее
[сравнение RAM и файла](RAM-CONTROL-VALIDATION.md) подтверждает только конкретный
транспорт intent: 0 против 24 секторов за шесть обновлений. Оно не означает
нулевой записи RouterOS в целом и не измеряет erase-циклы flash.
