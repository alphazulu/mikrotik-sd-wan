# Филиалы за операторским NAT

Русский | [English](CGNAT-VALIDATION.en.md)

Проверка кандидата продолжается. Этот документ пока не объявляет пройденными
матрицу отказов и проверки с локальным контейнером.

Контроллер остаётся на каждом MikroTik: RouterOS либо локальный Rust-контейнер
scratch без privileged. Филиалы инициируют WireGuard к доступному головному
узлу, который узнаёт адрес и порт по аутентифицированным пакетам.
Схема требует доступного головного узла. Прямая связность двух произвольных
симметричных NAT этим механизмом не обеспечивается.

## Новый изолированный стенд

У двух филиалов по два WAN, подключённых через независимые операторские NAT,
которые разрешают только исходящие соединения. Филиал A — x86 с лицензией
уровня 6, филиал B и головной узел — CHR; везде RouterOS 7.24.5.
Пять принадлежащих прогону Linux namespace изображают операторов, интернет
и две локальные сети. Каждый оператор отклоняет исходные адреса другого.
Входящего DNAT и прямого маршрута между локальными сетями через WAN нет.

У каждого филиала два туннеля WireGuard и два пути OSPF. Для обычного интернета
предпочтителен WAN1; отдельная политика по источнику строго выбирает WAN2.
Межфилиальные сети исключены из интернет-маркировки и NAT. Трафик запускается
после проверки соседств Full и установленных маршрутов.

## Ошибка холодного запуска второго WAN

Стенд выявил существующую UDP-запись с локальным адресом WAN1 при отправке
через WAN2 без исходящего NAT. Нужное правило masquerade уже существовало,
но первый пакет этого соединения через него не прошёл. Оператор правильно
отбрасывал такие пакеты.

Удаление только наблюдаемой записи с конкретным локальным портом и удалённым
адресом/портом восстановило оба резервных пути. Независимая проверка подтвердила
53 снимка с сохранением 12 записей conntrack для межфилиального трафика и восемь
новых интернет-потоков по захваченным пакетам. Это диагностическое вмешательство
подтверждает причину; автоматическая работа контроллера им не подтверждается.

Кандидат добавляет ограниченную проверку первого источника для инициирующих
overlay-пиров. Адрес после NAT сравнивается с действующими локальными адресами
выбранного WAN. Удаляется только запись собственного UDP-порта к конкретному
удалённому адресу/порту, если её исходящий адрес принадлежит другому интерфейсу.
Корректный masquerade, дополнительные адреса выбранного WAN и неизвестные
внешние адреса сохраняются. Ответные пиры и внутренние TCP/UDP-соединения
в эту проверку не входят.

Проверка работает в RAM не более 30 секунд после готовности WAN и завершается
раньше при обнаружении соответствующей локальной записи. Периодической записи
на носитель она не добавляет. Проверенный неизменившийся транспорт повторно
не сканируется. Девять native-кейсов проверяют неправильный, правильный,
дополнительный, внешний, отсутствующий и некорректный источник; удаление реальной
записи и сохранение остальных проверяются трафиком.

## Доказательства и ограничения

Ошибки первых вариантов стенда и синтаксическая ошибка кандидата сохранены как
неудачные прогоны. Защищённая установка выполнила откат после синтаксической
ошибки; ресурсы освобождены, хеши исходных образов сохранены. Последующая ошибка
импорта тестового адаптера выявлена проверкой исходников до создания роутеров.

API вернул успех для dry-run импорта заведомо ошибочной библиотеки. Поэтому
успешный ответ API на dry-run не используется как критерий корректного разбора.
На новом тестовом роутере результат настоящего импорта наблюдается через
RouterOS onerror: ошибочный контроль должен отклоняться, текущая библиотека —
приниматься. Дополнительно проверяется неизменность настроек пересылки трафика.

Код контроллера не менялся после кандидата 7efadbe; снимок
c18330214a0a06abc339e7a7fd884545264d7c5c содержит только исправления
проверочного кода RouterOS. Его дерево —
e111b0bcd359684cf084046156606438a52ef87f. Девять вариантов источника
и наблюдение настоящей ошибки импорта независимо проверены на новом x86.

Следующий полный прогон остался неудачным из-за немедленной проверки старой
записи после смены NAT-адреса и порта. Независимая проверка ранее выполненных
этапов этого же прогона подтвердила 48 двунаправленных интернет-потоков по
пакетам, четыре сохранявшихся межфилиальных потока и 222 снимка с 12 записями
conntrack. Пройдены пять случаев отказа/возврата WAN и смена только NAT-порта.
Это ограниченный подтверждённый результат, а не PASS всего прогона.

Отдельный последующий прогон подтвердил в RouterOS смену NAT-порта и адреса/порта,
потерю и восстановление интернет-SLA с сохранением межфилиального трафика.
Независимо сверены ещё 16 интернет-потоков и 83 снимка с 12 записями conntrack.
Удаление старой записи наблюдалось за 1,36 с и 0,86 с в этих двух случаях;
проверка ограничена десятью секундами. Это наблюдения стенда, а не гарантия
времени на физическом оборудовании.

В том же прогоне локальный Rust-контейнер установлен с сохранением
межфилиальных соединений. Затем прошли пять контейнерных случаев отказа/возврата
WAN. Независимая проверка охватила 56 интернет-потоков в этом прогоне,
462 уникальных снимка и 11 этапов сохранения conntrack, включая нативную часть.

Весь этот прогон сохранён как неудачный из-за следующего NAT-теста. RouterOS
корректно преобразовал активный исходящий порт WireGuard с 51821 в 17875,
а тест пытался изменить старую операторскую запись с портом 51821.
Conntrack RouterOS, таблица оператора и аутентифицированный адрес пира на хабе
независимо подтвердили активный порт 17875. Исправление выбора записи проверено
семью тестами и воспроизведением настоящей трассы. Оставшийся прогон сначала
определяет активную запись после masquerade, затем меняет только её на операторе.

Ожидаются оставшиеся проверки NAT/SLA в контейнере и штатная перезагрузка
нативного и контейнерного узла с новыми SLA и соединениями. Пройденные матрицы
физического отказа WAN повторно не запускаются. Виртуальный стенд не подтверждает
физическое LTE-радио, производительность ARM и устойчивость аппаратной флеш-памяти.

## Официальные источники

В актуальном справочнике [WireGuard peers](https://manual.mikrotik.com/docs/cli-reference/interface/wireguard/peers/)
описаны обновление адреса по аутентифицированным пакетам и persistent keepalive.
[Configuration management](https://manual.mikrotik.com/docs/getting-started/configuration-management/)
описывает dry-run импорта. Возможности сверяются с целевой RouterOS 7.24.5.
Раздел NAT нового руководства при проверке был недоступен; прежний официальный
[справочник NAT](https://help.mikrotik.com/docs/spaces/ROS/pages/3211299/NAT)
объясняет сохранение решения NAT по первому пакету соединения.

В актуальном [справочнике conntrack](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/connection-tracking/)
описаны исходные и ответные адреса/порты, используемые для сопоставления
соединения после NAT. Целевая проверенная версия — RouterOS 7.24.5.
