# Филиалы за операторским NAT

Русский | [English](CGNAT-VALIDATION.en.md)

Проверка уточнённого исправления источника продолжается. Чистая установка
контейнера выявила ещё один, непостоянный случай с обратным направлением
conntrack после предыдущих ограниченных проверок. Их результаты сохраняются
для указанных исходников и сценариев; новый кандидат ими не подтверждается.

## Схема и исходники

У двух филиалов по два WAN за независимыми операторскими NAT, разрешающими
исходящие соединения. Оба филиала инициируют WireGuard к доступному хабу,
который узнаёт источник по аутентифицированным пакетам. Доступный хаб обязателен;
прямая связность двух произвольных симметричных NAT этой схемой не обеспечивается.

Филиал A — x86 с лицензией уровня 6; филиал B и хаб — CHR. Везде RouterOS
7.24.5. Пять принадлежащих прогону Linux namespace изображают операторов,
контрольные и эхо-цели интернета и две LAN. Цели имеют зарезервированные адреса
стенда; настоящий провайдерский аплинк не используется. Каждый оператор
отклоняет исходные адреса другого. Входящего DNAT и прямого маршрута между
филиалами через физические WAN нет.

У каждого филиала два пути WireGuard/OSPF. Обычный интернет предпочитает WAN1;
отдельная политика по источнику строго выбирает WAN2. Межфилиальные префиксы
исключены из интернет-маркировки и NAT. Трафик допускается после проверки
соседств Full **и установленных маршрутов**: по два соседства в филиалах,
четыре на хабе.

Исторические трассы 231, 233 и 236 относятся к замороженному дереву
e111b0bcd359684cf084046156606438a52ef87f. Публичный runtime-коммит
[48b0742](https://github.com/alphazulu/mikrotik-sd-wan/commit/48b074272d775f5f78c5ec00b0a5f92f664eff73)
имеет точно такое же дерево. Уточнённый кандидат отдельно заморожен в дереве
71afaa5bf64ca159e8057b8beaee38e2418d67dc. Новая матрица отказов ещё выполняется;
итоговый PASS этих исходников пока не заявляется.

## Исправление источника второго WAN при холодном запуске

Первый стенд выявил исходящую UDP-запись с локальным адресом WAN1 при отправке
через WAN2 без NAT. Оператор правильно отклонял такой источник. Удаление только
точно наблюдаемой транспортной записи восстановило резервные пути; это было
диагностическое вмешательство, а не автоматическая приёмка.

Позже чистая установка локального контейнера завершилась ошибкой в обратном
направлении: исходно входящая запись имела источник ответа WAN1 при привязке
туннеля к WAN2. Старая проверка охватывала только исходные исходящие записи
и заканчивалась после первой подходящей. Прогон 239 остаётся неудачным.
Другой чистый запуск старой версии, 240, поднял все четыре пути и не воспроизвёл
такую запись; запланированное ручное удаление не выполнялось. Сбой непостоянный.

Уточнённая функция RouterOS проверяет оба направления записи собственного
UDP-порта к конкретному удалённому адресу/порту. Для исходно исходящих записей
используется reply-dst-address, для исходно входящих — reply-src-address.
Исходный локальный источник или назначение должны принадлежать маршрутизатору.
Удаляется только запись, чей источник после NAT принадлежит другому известному
локальному интерфейсу. Корректный masquerade, дополнительные адреса выбранного
WAN и неизвестные внешние источники сохраняются. Ответные пиры, внутренние
TCP/UDP, другие порты и удалённые адреса эта проверка не затрагивает.

Проверка больше не заканчивается после первой найденной записи. Она выполняется
при недоступности внутренней пробы пира и ещё 30 секунд после последнего такого
наблюдения. Возврат WAN, изменение транспорта и старое состояние модуля в памяти
открывают новое окно. После устойчивого восстановления и истечения окна
неизменившийся транспорт пропускает опрос адресов и conntrack. Инвентарь ограничен
1024 адресами. Состояние остаётся в RAM; периодическая запись на носитель не
добавляется. Нулевые записи всей RouterOS этим не подтверждаются.

Реальный импорт RouterOS и все 21 нативная проверка источника и окна восстановления
прошли на уточнённых замороженных исходниках. Новая матрица чистой установки
контейнера/нативного режима и её итоговая независимая сверка ещё не завершены.

## Независимо проверенные результаты

| Трасса и подтверждённый объём | Новые интернет-потоки TCP/UDP с двунаправленной проверкой пакетов | Сохранение межфилиального трафика |
|---|---:|---|
| 231: отказ WAN1 у A, возврат, отказ у B, отказ у обоих, возврат; смена NAT-порта | 48 | Четыре потока, 12 записей conntrack, 222 уникальных снимка |
| 233: нативные NAT-адрес/порт и потеря/возврат интернет-SLA; переход в контейнер; пять контейнерных отказов/возвратов WAN | 56 | Четыре потока, 12 записей, 462 уникальных снимка |
| 236: штатные перезапуски RouterOS и контейнера; оставшиеся контейнерные NAT/SLA | 40 | Две новые группы после перезапусков, по четыре потока и 12 записей, 397 снимков |

Исторические результаты включают **144 новых интернет-потока в трёх отдельных стендах**;
они не подтверждают уточнённый кандидат и неудачный случай чистой установки.
Повторяющиеся снимки исключены внутри каждого прогона. Сохранение потоков и
ID conntrack между стендами или через перезагрузку не заявляется.

Дополнительно подтверждены:

- Четыре автоматически поднявшихся пути WireGuard с маршрутами OSPF;
  межфилиальный трафик остаётся без маркировки и NAT.
- Существующие межфилиальные TCP/UDP и их записи conntrack сохраняются при
  переключении WAN, смене аутентифицированного адреса и переходе в локальный контейнер.
- Хаб узнаёт смену NAT-порта и адреса/порта без изменения endpoint через API
  компьютера. Старые внешние записи удаляются с сохранением остальных туннелей.
- При отказе обеих интернет-SLA у A и работающих физических WAN блокируются
  четыре новых TCP/UDP-подключения. Межфилиальные WireGuard/OSPF остаются доступны;
  восстановление возвращает предпочтительный WAN.
- Штатные перезапуски сбрасывают uptime, сохраняют лицензию уровня 6,
  собирают свежие SLA и восстанавливают четыре пути и новые соединения.
  Предыдущие тестовые сессии специально останавливаются до перезапуска.
- Пройдены девять нативных вариантов источника. Исходники и образ локального
  scratch-контейнера не менялись; сохранена привязка к 100% покрытия исполняемых
  строк и функций юнит-тестами. CI включает base, web, main и браузерный JavaScript.
- Освобождены собственные процессы, namespace и девять портов управления.
  После очистки независимо сверены хеши исходных образов x86/CHR.

## Сохранённые ошибки и уточнение наблюдения

Полные отчёты 231 и 233 остаются неудачными; таблица использует их независимо
подтверждённые успешные части. В 231 немедленная проверка старой записи
предшествовала наблюдению её удаления. Следующий прогон с тем же контроллером
зафиксировал удаление за 1,36 с и 0,86 с в двух нативных случаях в пределах
десятисекундного окна. Это наблюдения стенда, а не аппаратная гарантия времени.

Следующий тайм-аут 233 был вызван допущением теста: RouterOS преобразовал
активный порт с 51821 в 17875, а тест менял старую операторскую запись 51821.
Conntrack, NAT оператора и аутентифицированный адрес хаба подтвердили активный
порт. Исправленный выбор только для чтения проверен семью тестами и настоящей
трассой. В живом прогоне 236 выбран порт 65463; операторские смены на 60001 и
60002 сохранили активную запись RouterOS, три остальных туннеля и межфилиальные
соединения. Захвачены оба направления UDP-трафика.

Ранние ошибки стенда, разбора и чтения результата сохранены отдельно.
Успешного ответа API на dry-run оказалось недостаточно для обнаружения
заведомо ошибочной библиотеки. На стенде настоящий импорт наблюдался через
RouterOS onerror: ошибочный контроль отклонён, текущая библиотека принята,
настроенная пересылка не изменилась. Повторное имя дочернего лога остановило
235 до перезапусков; отдельный прогон 236 исправил это имя.

## Границы и источники

Эти проверки не подтверждают физическое LTE/радио, производительность ARM,
прямое прохождение симметричных NAT и устойчивость аппаратной флеш-памяти.
Прежние смешанные WAN, восстановление питания и 48-часовая приёмка сохраняют
свои исходники и объём проверки.

Официальный [справочник пиров WireGuard](https://manual.mikrotik.com/docs/cli-reference/interface/wireguard/peers/)
описывает обновление адреса по аутентифицированным пакетам и keepalive.
[Поля conntrack](https://manual.mikrotik.com/docs/cli-reference/ip/firewall/connection/)
описывает исходные и ответные поля для сопоставления.
[Управление конфигурацией](https://manual.mikrotik.com/docs/getting-started/configuration-management/)
описывает диагностику импорта. Актуальная страница NAT при проверке была
недоступна; прежний официальный [справочник NAT](https://help.mikrotik.com/docs/spaces/ROS/pages/3211299/NAT)
объясняет сохранение решения по первому пакету. Текущий справочник показывает 7.26;
проверенная RouterOS — 7.24.5.
