# Разбор CPU SD-WAN

Русский | [English](CPU-ATTRIBUTION.en.md)

Диагностические переключатели действуют только в одноразовой лабораторной VM. Остановленный контроллер не обеспечивает failover.

RouterOS 7.24.5 x86 L6, 1 vCPU/1024 MiB, virtio, 1000 новых TCP-соединений/с. Два повтора: 120 с прогрева + 30 с измерения; профиль 20 с внутри окна. Второй порядок обратный.

CPU RouterOS, категории профилировщика и CPU всего QEMU измеряются отдельно. QEMU включает потоки ввода/вывода; 100% означает одно логическое ядро хоста.

Среднее двух повторов; диапазон — наблюдавшиеся min/max, не доверительный интервал. Разности условные, не независимые доли общего CPU.

## Условные разности

| Компонент | Показатель | Среднее, п.п. | Диапазон, п.п. |
|---|---|---:|---:|
| controller | resource_cpu_percent | 28.07 | 26.17–29.97 |
| probes | resource_cpu_percent | 6.00 | 2.67–9.33 |
| mangle_policy_routing | resource_cpu_percent | 0.13 | -3.47–3.73 |
| NAT_and_auto_conntrack | resource_cpu_percent | 3.93 | -3.07–10.93 |
| resource_observer_profile_metric | profile_cpu_percent | 4.61 | 1.61–7.61 |
| resource_observer_host_QEMU_metric | qemu_host_cpu_percent | 0.10 | -0.09–0.28 |

Опрос ресурсов отключён только в observer-paused: CPU RouterOS там неизвестен. Сравнение наблюдателя использует профиль и QEMU отдельно.

Обход маркировки использует фиксированный маршрут main через WAN1, обход NAT — обратный маршрут на Linux-пире. Дополнительная проверка той же конфигурации показала enabled=auto: active-ipv4=true при обходе маркировки и false после отключения NAT. Поэтому столбец NAT включает изменение автоматической активации conntrack; чистая цена NAT не изолирована. Эти состояния проверяют затраты, не SLA/защиту от утечек.

Первое успешное baseline-окно сохранено из предыдущего запуска, остановленного защитной проверкой отсутствующего disabled в NAT print. Состояние правила прочитано явно через get, все переключатели проверены до новых нагрузок. Старый запуск остаётся failed; его успешное окно не повторялось.

Это виртуальный стенд; аппаратная производительность ARM/ARM64 и максимальная пропускная способность не подтверждаются. Исходники правил, контроллера и контейнера выпуска v0.3.0 не изменялись.

Категории описаны в [Profiler MikroTik](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/profiler/); поведение auto — в [Connection tracking](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/connection-tracking/). Формат API и переключение проверены на 7.24.5; текущая документация относится к 7.26.

## Вывод и приоритет оптимизации

Главный подтверждённый резерв — периодический цикл `sdwan-controller`:
при его остановке CPU RouterOS снижался на **26,17–29,97 п.п.** (среднее 28,07).
Остановка Netwatch-проб дополнительно давала **2,67–9,33 п.п.** (среднее 6,00).
Это условные разности диагностических состояний, а не готовая экономия рабочего
контроллера: сохранять требуемые SLA и failover при оптимизации обязательно.

Для маркировки/policy routing разности меняли знак: −3,47 и +3,73 п.п.
Для совместного NAT/auto-conntrack: +10,93 и −3,07 п.п. Двух повторов недостаточно,
чтобы надёжно выделить эти меньшие эффекты. Baseline изменился на 4,07 п.п.
Остановка только внешнего самплера ресурсов дала 1,61–7,61 пункта по метрике
профилировщика, но практически не изменила CPU всего QEMU (−0,09…+0,28 пункта).
Это не оценка всех API-вызовов контейнера; основной вывод о цикле RSC устойчивее.

Первый прототип оптимизации следует готовить в общей нативной части:

1. Измерить отдельно разрешение WAN/reconcile, чтение Netwatch, применение
   решений и сериализацию статуса. Профиль console показывает общий класс,
   а не стоимость конкретной строки скрипта.
2. Проверить пакетное чтение управляемых объектов вместо повторных `find/get`
   внутри циклов и RAM-кэш неизменённой конфигурации. Сохранить обнаружение
   смены адресов, пропавших/дублированных правил и свежесть SLA.
3. Сравнить прототип на том же стенде, затем проверить переключение, симметрию
   ответов, selective conntrack и RSC/container parity. Частоту SLA не снижать
   ради благоприятного CPU-числа.

На момент этого исследования исполняемый код не менялся. В следующей ограниченной
итерации реализованы свежие снимки без постоянного кэша конфигурации: [результаты](NATIVE-CYCLE-OPTIMIZATION.md).
Опубликованный тег v0.3.0 и его принятые файлы сохранены.
