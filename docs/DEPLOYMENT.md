# Защищённая установка на RouterOS

Русский | [English](DEPLOYMENT.en.md)

GUI и CLI `apply` передают выполнение локальному RouterOS scheduler. API используется для подготовки файлов, наблюдения и подтверждения. Watchdog работает на самом роутере; закрытие конфигуратора не отключает восстановление.

## Основания по документации MikroTik

Проверено 23 октября 2026 по актуальному manual (на сайте версия 7.26), исполнение проверяется отдельно на целевой CHR **7.24.5**.

[Configuration Management](https://manual.mikrotik.com/docs/getting-started/configuration-management/) описывает последовательный импорт, остановку на ошибке и Safe Mode. Safe Mode включается через WinBox или терминал Ctrl+X/F4; изменения других сессий также попадают под него. История ограничена примерно 100 действиями: при переполнении Safe Mode автоматически освобождается, автоматическая отмена перестаёт действовать. Поэтому он не является гарантией для большого SD-WAN пакета. У [CLI safe-mode](https://manual.mikrotik.com/docs/cli-reference/safe-mode/) документировано чтение состояния; публичного setter для включения через API нет.

[Backup](https://manual.mikrotik.com/docs/getting-started/configuration-management/backup/) сохраняет бинарную конфигурацию, включая чувствительные параметры. Используем пароль и `aes-sha256`, `dont-encrypt=no`. Загружать backup следует на том же устройстве и версии RouterOS. `load` перезагружает роутер; скрипту нужен явный пароль. Базы Dude и User Manager в него не входят. Произвольные файлы проекта сохраняем отдельно.

[Files](https://help.mikrotik.com/docs/spaces/ROS/pages/2555971/Files): при наличии каталога `flash` постоянные файлы должны находиться в нём. На некоторых устройствах запись задерживается до 40 секунд; внезапное отключение питания может оставить пустые файлы. Эта реализация не обещает атомарности при потере питания.

[Scripting](https://manual.mikrotik.com/docs/developer-guides/scripting/) уточняет права: обычный `/system/script/run` из scheduler наследует policy записи scheduler. Поэтому необходимые права явно назначены обоим заданиям, `dont-require-permissions` не используется.

## Последовательность

1. Проверка identity, версии, интерфейсов, конфликтов, прав `read,write,policy,test,sensitive,reboot` и отсутствия другой незавершённой установки. Активный Safe Mode нужно завершить перед началом.
2. Локальный диагностический снимок `runtime/pre-native-*.json`. На роутер загружаются запрос с уникальным токеном и три вспомогательных RSC. Этот этап не меняет маршрутизацию.
3. Bootstrap архивирует прежние JSON/RSC, регистрирует worker/watchdog и создаёт зашифрованный `sdwan-before-<token>.backup`. Клиент проверяет heartbeat watchdog до загрузки нового сетевого пакета.
4. Новый JSON и восемь RSC ядра загружаются и читаются обратно для сверки. Только затем отправляется arm-токен. Watchdog запускает worker через отдельный scheduler.
5. Worker локально импортирует установщик. Любая пойманная ошибка переводит транзакцию в failed. Watchdog проверяет свежий статус, revision и heartbeat нового контроллера.
6. Конфигуратор открывает **новое соединение API**, проверяет identity, revision и выбранный рабочий default WAN; затем отправляет ACK с токеном. Одна сохранившаяся старая TCP-сессия не считается подтверждением новой доступности.
7. Watchdog фиксирует committed и отключает оба вспомогательных scheduler. SD-WAN controller продолжает работать самостоятельно.

Стандартный срок подтверждения — 120 секунд от подготовки. CLI Python API допускает 30–600 секунд для испытаний. Контроллер должен успеть прогреться, а API — переподключиться в этот срок. Если все WAN не проходят SLA, автоматического подтверждения установки нет.

## Аварийное восстановление

При ошибке worker/контроллера, abort, отсутствии ACK до срока или перезагрузке до подтверждения watchdog останавливает worker и контроллер, возвращает старые файлы и выполняет `/system/backup/load`. Это восстанавливает всю конфигурацию из снимка с перезагрузкой. После загрузки watchdog ещё раз восстанавливает файлы, отмечает rolled-back и отключается. Повторная установка старого пакета через внешний API для аварийного отката не нужна.

Восстановление затронет и посторонние изменения, внесённые **после** backup. На время установки требуется исключить параллельное редактирование устройства. Сессии при перезагрузке прерываются; бесшовности здесь нет. Повреждение диска, отключение watchdog вручную, нехватка ресурсов и отказ самого RouterOS не покрываются этой гарантией.

SDK сохраняет предыдущие bootstrap/worker/watchdog до их перезаписи, затем добавляет проверенные архивы в previous manifest подготовленного журнала до загрузки payload/arm. Откат возвращает восемь RSC ядра, три служебных RSC и staging/active/baseline JSON; отсутствовавшие файлы удаляются. Текущие recovery jobs остаются механизмом восстановления, а журнал и backup — для диагностики. Бинарный снимок делается после регистрации этих заданий, до сетевых изменений.

`sdwan-deploy-current.json` указывает на журнал `sdwan-txn-<token>.json`. Он содержит фазу, срок и причину восстановления, а также пароль backup: доступ к файлам и `sensitive` должен быть ограничен. Локальная копия ключа — `runtime/recovery-<token>.json`, исключена из Git. На NTFS защита определяется Windows ACL. Пароль не печатается. Проверено на CHR: `/file add contents=...` журналирует данные, поэтому файлы создаются пустыми и заполняются отдельным `set contents`; пароль не попадает в RouterOS log при этой операции.

Без настройки `maintenance` архивы и backups автоматически не удаляются. Опциональный `maintenance.backup_keep` включает безопасную очистку один раз после committed; также доступен отдельный CLI dry-run/execute. Текущая транзакция, сохранённые точки восстановления и их зависимости защищены. Подробности: [MAINTENANCE.md](MAINTENANCE.md). Recovery keys на компьютере не удаляются автоматически.

## Два значения отката

**Аварийный откат установки** возвращает бинарный backup непосредственно перед последним изменением. **«Откат к исходному»** / CLI `rollback` удаляет собственные SD-WAN объекты и восстанавливает baseline-флаги маршрутов, FastTrack, rp-filter и сохранённые routing options DHCP/PPPoE клиентов и APN LTE. Последняя операция тоже выполняется worker/watchdog с резервной копией и свежим API-подтверждением; если она оборвёт управление, вернётся состояние перед её началом.

## Экспорт и ручное обслуживание

Стандартный комплект содержит 12 файлов: JSON и 11 RSC (controller, dataplane, links, overlay, vpn, dns, install, rollback, deployment, deploy-worker, deploy-watchdog). Список `FILES` находится в `sdwan.py`. Для защищённой установки используйте GUI или CLI: они соблюдают порядок архивирования **до** перезаписи старого пакета и отправляют подтверждение.

Прямой `/import sdwan-install.rsc` применяет правила сразу и обходит описанную защиту. Это низкоуровневый способ для лаборатории или локальной консоли. При наличии `flash/` укажите этот префикс. Контроллер после любой установки остаётся полностью на RouterOS.

LTE baseline хранится отдельно по APN профилю до изменения add-default-route. Общий профиль согласуется один раз; unselected shared modem блокирует установку. APN distance/DNS/credentials не переписываются. Бинарный аварийный restore возвращает APN вместе с остальной конфигурацией.

Группы адресов, составные селекторы и порядок политик устанавливаются тем же локальным worker/watchdog. План явно показывает пересечения и необходимость переклассификации исходящих соединений. После такой редакции managed client sessions пересоздаются; native incoming API/probes не входят в эту очистку. Неизменные selectors/groups/order сохраняют сессии при reapply. Аварийный binary restore возвращает прежние группы, правила и согласованный пакет.


Локальные `runtime/` отчёты, учётные данные и снимки устройств не входят в
репозиторий. Методика повторения проверок: [TESTING.md](TESTING.md).
