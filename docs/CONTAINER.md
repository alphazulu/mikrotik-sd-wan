# Локальный Rust-контроллер в контейнере

Контроллер работает в контейнере **на самом MikroTik**. Его образ — `FROM scratch`
с одним статическим Rust/musl исполняемым файлом. Дистрибутива, shell, БД,
веб-сервера, shared libraries и SDK в образе нет. Пароль и настройки подключаются
двумя отдельными каталогами только для чтения.

Rust выбирает WAN по готовности, SLA и порядку каналов в политике. RouterOS
измеряет каналы, поддерживает DHCP/PPPoE/LTE/APN, маркирует соединения,
проверяет допустимость решения и применяет маршруты/NAT. Тот же единственный
скрипт и scheduler RouterOS держат прогретый резерв: при потере контейнера или
его связи с API выбор WAN продолжает нативный алгоритм. Отдельного внешнего
сервиса для работы SD-WAN нет.

## Запуск через конфигуратор

1. Установите на целевом устройстве RouterOS **7.24.5** и соответствующий пакет
   `container`. Разрешите `container=yes` в device-mode с требуемым физическим
   подтверждением. Подготовка в GUI этого подтверждения не обходит.
2. Из `dist/container/` выберите образ: `arm64` для ARM64, `armv5` для ARM,
   `amd64` для CHR/x86_64. Загрузите `.tar.gz` или `.tar` на MikroTik через Files
   в WinBox либо имеющийся способ передачи файлов. Cross-build ARM не заменяет
   испытание на физическом устройстве.
3. Запустите `Configure-SD-WAN.cmd`, подключитесь по API, выберите WAN и создайте
   конфигурацию. Во вкладке **«Контроллер»** выберите **«Локальный контейнер Rust»**.
4. Задайте свободную частную сеть `/30`, каталог данных на MikroTik и имя уже
   загруженного архива. GUI добавляет эту сеть в `local_networks`, чтобы ответы
   API шли обратно в veth через main. Подготовка отклоняет пересечения с
   существующими адресами и маршрутами main, включая агрегаты к филиалам.
5. Нажмите **«Подготовить контейнер»**. Создаются bridge/veth, правила доступа,
   отдельный API-пользователь, файлы и mounts. Архив импортируется, контейнер
   остаётся остановленным. Политики SD-WAN этой кнопкой не устанавливаются.
6. Просмотрите **«План изменений»**, затем нажмите **«Установить на MikroTik»**.
   Локальный worker сохраняет зашифрованный backup, применяет пакет и запускает
   контейнер. Watchdog требует действующей аренды контейнера и подтверждения
   через новое API-соединение. При ошибке/таймауте восстанавливает предыдущую
   конфигурацию и файлы и перезагружает RouterOS.
7. В **«Диагностике»** виден фактический исполнитель решений: контейнер либо
   резервный скрипт. Устаревший снимок не считается подтверждением работы
   контейнера. Каналы, SLA, группы и правила клиентов настраиваются теми же
   средствами, что у RSC backend.

Нативный backend остаётся самостоятельным: выберите **«Скрипт RouterOS»** и
установите конфигурацию. После подтверждённой смены backend SDK останавливает
свой контейнер и отключает его автозапуск. Каталог данных сохраняется.

## JSON и CLI

Добавьте к обычной конфигурации следующий фрагмент; WAN/SLA/политики остаются
в том же файле. Пароля в нём нет:

```json
{
  "controller_backend": "container",
  "container": {
    "subnet": "172.31.255.0/30",
    "storage": "disk1/sdwan-container",
    "image_file": "disk1/sdwan-controller-arm64.tar.gz",
    "poll_ms": 1000,
    "memory_max_bytes": 16777216
  }
}
```

Сеть контейнера должна явно входить в `local_networks`. Интервал допускается
500–2000 мс, лимит памяти — 8–64 МиБ; 16 МиБ — лимит, а не заранее занятая память.
Полный пример для отдельного CHR — `config/examples/container.json`.

```sh
python3 sdwan.py --config config/examples/container.json --url api://127.0.0.1:38728 --credentials runtime/container-lab/project/runtime/credentials.json --expect-identity sdwan-container-edge container-prepare
python3 sdwan.py --config config/examples/container.json --url api://127.0.0.1:38728 --credentials runtime/container-lab/project/runtime/credentials.json --expect-identity sdwan-container-edge plan
python3 sdwan.py --config config/examples/container.json --url api://127.0.0.1:38728 --credentials runtime/container-lab/project/runtime/credentials.json --expect-identity sdwan-container-edge apply
```

Это адреса и учётные данные только изолированной лаборатории проекта. Для
своего устройства используйте его URL, identity и отдельный файл учётных данных.
В проекте рабочий MikroTik не подключался и не менялся.

Подготовка проверяет владельцев объектов и существующие permissions; чужие
bridge/veth/контейнер/mount list с зарезервированным именем не перезаписываются.
API-пользователь ограничен адресом контейнера и правами
`read,write,policy,test,sensitive,api`; остальные права явно отключены. На 7.24.5
эти права нужны для чтения публичных globals и записи intent-файла.
RouterOS предоставляет общие права API, без ACL на отдельные пути команд.
Нативный API используется только внутри закрытого veth; пересылка трафика
из/в эту сеть блокируется. Контейнеру не требуются Интернет и DNS-запросы.

## Выбор WAN и восстановление

Пакет сохраняет восемь RSC и JSON. Для контейнерного backend генерируются
варианты controller, installer и watchdog; второго писателя маршрутов нет.
Входящие соединения со всех WAN и ответы через соответствующие таблицы
обрабатывает общий проверенный dataplane. При смене WAN удаляются только
соответствующие управляемые записи conntrack.

Intent содержит boot fence, поколение конфигурации, revision, случайный nonce
процесса и возрастающий sequence. Адаптер отклоняет отсутствующие/неверные
поля, старые поколения и команды чужого владельца. Принятый WAN повторно
проверяется против **текущего** SLA перед применением. Изменение конфигурации
обновляет поколение даже при сохранённом revision; перезагрузка меняет boot fence.

Heartbeat проходит через отдельное правило в динамический address list
RouterOS с timeout 6 секунд: это RAM, без периодических записей на flash.
Сначала процесс подтверждает этот путь, затем записывает intent. Стабильный
выбор не переписывает файл. При недоступном heartbeat записи не повторяются
на каждом опросе. Истечение аренды возвращает выбор нативному алгоритму;
реальное время зависит также от цикла scheduler и загрузки RouterOS.
Смена владельца при неизменном маршруте не сбрасывает клиентские соединения.

Для замены версии образа требуется повторный импорт остановленного своего
контейнера: подготовка существующего root-dir его содержимое не обновляет.
Настройки WAN/SLA/политик меняются обычной установкой JSON без пересборки образа.
Подготовка инфраструктуры контейнера — отдельный шаг; откат неудачной установки
возвращает состояние перед этой установкой. Кнопка «Откат к исходному» возвращает
исходную сетевую конфигурацию SD-WAN и останавливает свой контейнер, сохраняя его файлы.

## Сборка минимального образа

Подготовка закреплённого Rust SDK и готовые release-архивы: [BUILD.md](BUILD.md).

```sh
python3 container-controller/build.py
```

Скрипт использует локальный Rust SDK в `runtime/toolchains`, `Cargo.lock`, LTO,
strip и статическую musl линковку. Проверяет ELF architecture и отсутствие
PT_INTERP/PT_DYNAMIC, формирует Docker-save tar и gzip без Docker daemon.
Размеры и SHA256 — `dist/container/build-report.json`. Для обычного Docker
создаются готовые контексты `dist/container/{amd64,arm64,armv5}/`, например:

```sh
docker build --platform linux/arm64 -t sdwan-controller:arm64 dist/container/arm64
```

В контексте только бинарник, Dockerfile и `.dockerignore`. Настройки, пароли,
исходники, toolchain и кэши в image не включаются.

## Проверки и границы

Текущая приёмка — [CONTAINER-VALIDATION.md](CONTAINER-VALIDATION.md).
Поддержка static/DHCP/PPPoE/LTE/APN использует общий нативный resolver и dataplane;
их предыдущая полная приёмка — [POLICIES-VALIDATION.md](POLICIES-VALIDATION.md).
Физические ARM/LTE-модемы и длительный нагрузочный тест не заменены CHR.
IPv6, DPI и миграция существующих OSPF/VPN-правил не добавлялись:
guard конфликтующих внешних маркировок сохранён.

Документация производителя: [Container](https://manual.mikrotik.com/docs/containers/),
[Device mode](https://manual.mikrotik.com/docs/system-information-and-utilities/device-mode/),
[API](https://manual.mikrotik.com/docs/developer-guides/api/).
Текущие руководства описывают 7.26, испытания проекта закреплены на 7.24.5.


Локальные `runtime/` отчёты, учётные данные и снимки устройств не входят в
репозиторий. Методика повторения проверок: [TESTING.md](TESTING.md).
