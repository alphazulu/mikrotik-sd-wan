# Соединения, симметрия WAN и очистка conntrack

Управление маршрутами, маркировкой и удалением conntrack выполняется на RouterOS. GUI только готовит и устанавливает конфигурацию. В комплект входят `sdwan-config.json`, пять RSC ядра и три RSC защищённой установки. Установщик сам импортирует `sdwan-dataplane.rsc` после создания FIB-таблиц.

## Метки и маршрутизация

| Трафик | Connection mark | Routing mark / таблица |
|---|---|---|
| Новое соединение, пришедшее через WAN | `sdwan-in-<wan>` | Входящий пакет продолжает INPUT или DNAT; ответ использует таблицу этого WAN |
| Исходящее соединение клиента | `sdwan-out-<policy>:<wan>` | Постоянная таблица выбранного WAN |
| Исходящее соединение самого MikroTik | `sdwan-router-<wan>` | Таблица фактического исходящего WAN |
| Контрольная проба с исходным IP WAN к заданной цели | `sdwan-probe-<wan>` | Постоянная таблица проверяемого WAN; исключена из очистки пользовательских сессий |

`prerouting` переходит в `sdwan-pre`, `output` — в `sdwan-output`, `postrouting` — в `sdwan-post`. Переходы располагаются перед остальными статическими mangle-правилами. Входящий connection mark назначается до DNAT. Ответ сервера за DNAT сохраняет эту метку и проходит через исходный WAN, даже если собственная исходящая политика сервера предпочитает другой канал. Ответ самого роутера получает routing mark в `output`.

Новые клиентские соединения классифицируются сначала по явным клиентским политикам, затем по default. Метка содержит и политику, и WAN: два клиента на одном провайдере могут переключаться и очищаться независимо. Уже маркированный поток не переназначается каждым пакетом. Непомеченные established/related потоки также могут получить метку, чтобы пропущенный первый пакет не оставлял соединение постоянно без маркировки.

Локальные адреса самого роутера и `local_networks` исключаются до назначения исходящего WAN. Входящие пакеты WAN не получают routing mark обратно в этот WAN: после маркировки соединения они продолжают обычную обработку. Это необходимо для INPUT, DNAT и доставки ответов клиентам.

Для каждой политики контроллер включает классификатор только выбранного WAN. Когда подходящего канала нет, отдельное правило направляет непомеченные пакеты в таблицу политики и не позволяет перейти к общей политике. `strict` сохраняет режим без резерва. В каждой постоянной WAN-таблице есть blackhole default с distance 254, исключающий обход через main при недоступном next hop.

Для начального route lookup локального ответа установщик создаёт source rules для выбранного IP и дополнительных IPv4 на этом WAN-интерфейсе. Это сохраняет возможность ответа на доступный WAN IP даже когда SLA отключил все default routes в main. После добавления/удаления дополнительных постоянных WAN IP повторите установку, чтобы согласовать source rules. Первичный DHCP/PPPoE/LTE IP, gateway и логический интерфейс разрешаются на RouterOS и обновляются локально при смене аренды/сессии; такой IP не сохраняется как дополнительный alias. См. [DYNAMIC-WAN.md](DYNAMIC-WAN.md). Физически недоступный канал не становится доступным за счёт маркировки.

Исходящие соединения самого роутера получают отдельную метку в postrouting до srcnat: условие `src-address-type=local` отделяет их от пересылаемых клиентских пакетов. Явно заданный source address проб остаётся привязанным к своему WAN, поэтому новая проверка неисправного канала не уходит через резерв.

Контрольные назначения выделены в списки `sdwan-probes-<wan>` и отдельную connection mark. Очистка обычных сессий роутера не обрывает SLA-пробы. Для DNS-пробы назначением служит DNS-сервер, для TCP/HTTP — host, для ICMP — icmp_target. Списки поддерживают IP и DNS-имена средствами [RouterOS Address-lists](https://help.mikrotik.com/docs/spaces/ROS/pages/130220135/Address-lists); DNS-разрешение контрольных имён должно быть доступно на самом устройстве.

## Что удаляется при переключении

Когда выбор политики меняется с WAN A на WAN B либо на `none`, контроллер:

1. Согласует маршруты и активный классификатор новых соединений.
2. Находит записи с точной прежней меткой `sdwan-out-<policy>:<wan-A>` и удаляет их.
3. Для смены default также удаляет `sdwan-router-<wan-A>`.
4. Публикует причину, прежний/новый WAN и количество удалённых записей.

Та же процедура выполняется при возврате на приоритетный канал. Если у двух клиентов WAN2, но возвращается только один, соединения другого клиента на WAN2 сохраняются. Общего `/ip firewall connection remove [find]` нет.

В течение трёх секунд после смены выбора контроллер дополнительно удаляет точные клиентские метки невыбранных WAN. Так закрывается окно для записей, созданных пакетами, которые уже находились в обработке во время переключения. Выбранная метка и другие политики этим проходом не затрагиваются.

При подтверждённом down WAN удаляются его ingress и router-originated метки. Отдельная деградация voice SLA не удаляет входящие сессии доступного канала. Другие работающие WAN и соединения управления через отдельный LAN/management-интерфейс сохраняются.

В состоянии доступны `conntrack_removed` и `last_cleanup.<policy>` с `from`, `to`, `removed`, `uptime_seconds`. В RouterOS log появляются `SDWAN conntrack ...`, рядом с `SDWAN state ...` и `SDWAN route ...`. Эти данные читаются кнопками «Состояние» и «Журнал решений».

Удаление записи conntrack не является отправкой TCP RST обоим концам. Приложениям может понадобиться переподключение. Смена публичного NAT IP не переносит существующую TCP-сессию на новый адрес бесшовно.

## Совместимость и установка

- FastTrack для управляемого трафика должен быть отключён. Мастер включает выбранные правила в план и сохраняет исходные disabled-флаги для отката.
- Чужие активные `mark-routing`, `mark-connection`, `route` и RAW `notrack` требуют согласования; установщик не отключает их автоматически. Собственные mangle-правила SD-WAN не блокируют повторную конфигурацию.
- Connection tracking должен быть включён (`auto` допустим). Установщик отклоняет явно выключенный tracking.
- `rp-filter=strict` меняется на `loose` с сохранением исходного значения для отката. Остальные значения остаются прежними.
- Сервисы управления, input/forward разрешения, DNAT и исходящий NAT остаются частью существующей конфигурации. Маркировка исправляет маршрут ответа; она не открывает закрытый firewall порт и не обеспечивает доступ через CGNAT.
- Метки `sdwan-*`, цепочки `sdwan-pre`, `sdwan-output`, `sdwan-post`, список `sdwan-local`, FIB-таблицы `sdwan-*` и комментарии `sdwan:v1:` зарезервированы для проекта.

План GUI/CLI показывает mangle, локальные списки, blackhole и source rules. Установка очищает опубликованный статус перед запуском нового контроллера и ждёт нового отчёта. При ошибке обновления или потере API-подтверждения независимый watchdog возвращает полный зашифрованный backup и файлы с перезагрузкой: [DEPLOYMENT.md](DEPLOYMENT.md). Нативный rollback удаляет собственные mangle/list/marks, восстанавливает сохранённые baseline-флаги и убирает объекты проекта.

Соединения, оставшиеся от конфигурации до установки без меток SD-WAN, требуют отдельного согласованного переноса/переподключения: автоматическая очистка гарантируется по управляемым меткам. Существующая NAT-привязка не переписывается простым присвоением connection mark. Бесшовный перенос уже работающих unmarked/FastTracked сессий не реализован.

PCC/веса по новым соединениям, приложение/порт как селектор политики, QoS и overlay остаются следующими этапами. Эта реализация обеспечивает выбор WAN по политике и SLA, симметрию и выборочную очистку, а не полную балансировку SD-WAN.

Native LTE использует interface gateway и текущий dynamic IPv4. Automatic default управляется через APN, а не через ip/dhcp-client; WAN source pins и selective conntrack используют общую логику динамического WAN. См. [LTE.md](LTE.md).

## Составные селекторы политик

Новые правила используют source/group, destination/group, входной L3 interface, protocol и src/dst ports. Native classifier и guard имеют одинаковые селекторы; в таблице каждой частной политики есть blackhole default254. Составные правила не создают широкое source-only routing rule. Меньший явный priority выполняется раньше; общая политика последняя. При изменении selectors/groups/order пересоздаются managed outbound client flows; входящие WAN API и probes сохраняются. При неизменном классификаторе повторное применение сохраняет клиентские потоки. Подробности — [POLICIES.md](POLICIES.md).


Локальные `runtime/` отчёты, учётные данные и снимки устройств не входят в
репозиторий. Методика повторения проверок: [TESTING.md](TESTING.md).
