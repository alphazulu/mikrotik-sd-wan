# Статистика в RAM и локальный веб-интерфейс

Опциональный модуль работает в том же Rust-контейнере на MikroTik. Маршруты,
conntrack и SLA продолжают обслуживать основной цикл и единственный исполнитель
RouterOS. Веб-интерфейс показывает состояние, графики и события; HTTP-команд
изменения настроек или маршрутов нет. Внешний сервер для него не нужен.

## Включение

По умолчанию модуль выключен. Минимальный образ `sdwan-controller-ARCH` собирается
без Cargo feature `web` и вообще не содержит HTTP-сервера. Отдельный образ
`sdwan-controller-web-ARCH` содержит сервер и встроенные HTML/CSS/JS. Даже этот
образ не открывает порт, не выделяет историю, не создаёт потоки и не читает
web-токен до явного включения `container.telemetry.enabled`.

1. Выберите локальный Rust backend в конфигураторе. Загрузите web-образ для своей
   архитектуры: amd64 для CHR/x86_64, arm64 или armv5 для соответствующего MikroTik.
2. На вкладке **«Веб и статистика»** включите модуль. Задайте период, размер
   истории, порт, разрешённые RFC1918 IPv4 сети и входные LAN/VLAN интерфейсы.
   Сети должны входить в `local_networks`. WAN, его PPPoE/VLAN носители, bridge и bridge-порты запрещены.
   Учитываются также include/exclude и явные members списка WAN, в
   [порядке RouterOS](https://manual.mikrotik.com/docs/cli-reference/interface/list/).
3. Остановите подготовленный контейнер перед изменением его файлов. Нажмите
   **«Подготовить контейнер»**, затем выполните защищённую установку SD-WAN.
   Подготовка проверяет web-entrypoint образа, RO mounts, права и API identity.
4. Нажмите **«Скопировать токен с MikroTik»**, затем **«Открыть веб-интерфейс»**.
   Браузер должен находиться за разрешённым LAN/VLAN и иметь маршрут через MikroTik
   к отдельной сети контейнера. URL — например `http://172.31.255.2:8080/`.
5. Вставьте токен на странице входа. Он остаётся в памяти страницы, без URL,
   localStorage или sessionStorage. Выход/перезагрузка страницы удаляют его.
   Конфигуратор очищает свой буфер обмена через 60 секунд, если он не изменился.

Полный лабораторный пример — [container-web.json](../config/examples/container-web.json).
Этот JSON использует синтетические адреса стенда; сначала получите реальные
настройки через мастер. Например, публичная часть настройки модуля:

```json
"telemetry": {
  "enabled": true,
  "sample_seconds": 10,
  "history_points": 360,
  "port": 8080,
  "allowed_sources": ["192.168.50.0/24"],
  "allowed_interfaces": ["bridge-lan"]
}
```

Это поле внутри `container`. Пароля или web-токена в JSON нет. Секрет — отдельные
32 случайных байта в виде 64 hex символов, файл `<storage>/secrets/web-token`,
в контейнере `/secrets/web-token`. Валидный токен переиспользуется при повторной
подготовке. Для ротации остановите контейнер, удалите только этот файл и снова
выполните подготовку. При отключении секрет не удаляется автоматически.

## Что видно

Карточки WAN показывают RTT, jitter, потери, состояние SLA выбранного профиля,
IP/интерфейс и скорости RX/TX. Таблица показывает выбранный WAN каждой политики
и число наблюдаемых переходов. Доступны состояния всех SLA-профилей, события,
графики и скачивание ограниченной истории в JSON на компьютер пользователя.

Скорости вычисляются из разности `rx-byte`/`tx-byte` выбранных интерфейсов,
без дополнительного трафика проб. При сбросе счётчика, смене интерфейса или
пропуске чтения неизвестные значения отображаются как `null`/«—». Это интерфейсный
трафик, включая служебный, а не биллинг провайдера и не статистика отдельных
приложений/клиентов. События относятся к текущей revision/boot/generation epoch.

Время «без healthy» считается только в наблюдаемых интервалах текущего запуска.
Длинные пропуски не превращаются в выдуманный простой. При остановке обновлений
старше 10 секунд страница явно показывает stale. Перезапуск контейнера, reboot
роутера и смена epoch очищают историю; долговременной SLA-отчётности здесь нет.

## Ограничения ресурсов

| Параметр | Значение |
|---|---|
| Интервал истории | 10 с по умолчанию, 5–60 с |
| История каждого WAN | 360 точек, максимум 600 |
| WAN / политики / состояния SLA | 16 / 64 / 1024 |
| События | последние 128 с ограниченными строками |
| Передача снимка из основного цикла | очередь 1, `try_send`, максимум 256 КиБ |
| API-счётчики | отдельная сессия, ответы до 64 КиБ / 32 строк |
| Потоки модуля | collector и HTTP, стеки по 128 КиБ |
| HTTP | заголовки 4 КиБ / 250 мс, ответ до 1 МиБ / 2 с |
| Частота HTTP | общий bucket 8 запросов, восстановление 2 запроса/с |

JSON сериализуется и отправляется после освобождения lock. Медленный клиент,
недоступный API счётчиков или занятая очередь не задерживают heartbeat. Ошибка
запуска веб-модуля оставляет основной контроллер работать. Образ остаётся
`scratch`, один статический бинарник, без shell, БД, Node.js и CDN.

## Накопитель и swap

Модуль не создаёт файлов данных, cache, access log, временных файлов, SQLite/WAL
или checkpoints. Кольца истории и событий остаются в RAM. Экспорт формирует
HTTP-ответ из RAM; файл сохраняет браузер на компьютере пользователя.
Явная подготовка один раз записывает настройки и секрет. Существующий механизм
intent контроллера по-прежнему записывает решение при смене WAN/claim: отсутствие
записей статистики не означает отсутствие любых записей RouterOS.

Подготовка выключает container logging. На CHR 7.24.5 проверено, что
`swap-max=0` возвращается как `unlimited`; поэтому задаётся минимальный положительный
лимит `swap-max=1`. Страничное округление зависит от ядра: этот лимит сам по себе
не считается доказательством отсутствия swap. Включение RAM-статистики дополнительно
требует отсутствия включённых swap-устройств в `/disk`. Глобальные диски не меняются.
Не включайте swap после этой проверки, если требуется хранение данных строго в RAM.
Параметры памяти/swap: [RouterOS containers](https://manual.mikrotik.com/docs/containers/),
[swap space](https://manual.mikrotik.com/docs/hardware/disks/).

## Доступ и API

Подготовка создаёт отдельный адресный список и точные forward-правила для
указанных LAN интерфейсов, адресов и TCP-порта контейнера. WAN drop идёт раньше
LAN accept, затем сохраняются общие запреты forwarding к/из контейнера. DNAT и
WAN-порт не открываются. Изменённые scopes/порядок/образ отвергаются при preflight.
Контейнер дополнительно проверяет IP источника и bearer-токен. HTTP предназначен
для доверенного LAN/VPN; встроенного TLS и публичного доступа нет.

| GET endpoint | Содержание |
|---|---|
| `/`, `/style.css`, `/app.js` | Встроенная оболочка, без секретов |
| `/api/status` | Текущий безопасный снимок, age/stale, ресурсы |
| `/api/history?max=120` | История, `max` 1–600 |
| `/api/events?since=0` | До 128 событий текущей epoch |
| `/api/export` | JSON истории и событий, attachment |

JSON требует `Authorization: Bearer <web-token>`. Токены в query запрещены.
POST/PUT/DELETE, чужие Origin, неоднозначные заголовки и лишние параметры
отклоняются. Нет CORS. Ответы содержат `no-store`, CSP и запрет iframe. Полная
конфигурация, API-пароль, owner nonce, intent, backups и журнал восстановления
в ответы не попадают. Код интерфейса не использует `innerHTML`.

## Обновление и откат

Смена `image_file` в GUI не заменяет файловую систему существующего контейнера.
Подготовка требует предварительного импорта web-образа. Обновляйте остановленный
контейнер с сохранением старого образа, настроек и секрета; `/container/save`
позволяет сохранить root-dir и параметры в архив. На время остановки работает
нативный fallback. Снимки статистики при замене не сохраняются.

Защищённая установка SD-WAN восстанавливает конфигурацию RouterOS, но **не является
откатом файловой системы образа контейнера**. Восстановление образа выполняется
отдельным импортом сохранённого архива и подготовкой соответствующих mounts.

Исходная архитектура: [STATISTICS-DESIGN.md](STATISTICS-DESIGN.md).
