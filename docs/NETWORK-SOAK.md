# Длительная проверка на CHR

`tools/network_soak.py` запускается на Linux/WSL и наблюдает существующий изолированный стенд с RouterOS
7.24.5. Решения о маршрутизации принимают сами MikroTik. Драйвер использует
только фиксированные loopback API стенда, проверяет identity/version и удерживает
общую блокировку `lab.lock` вместе с отдельной `network-soak.lock`.

Перед запуском должны завершиться функциональные проверки текущего кода,
включая DHCP/PPPoE, очистку внешнего UDP, повторное применение и полный откат.
Нужны чистый проверенный Git-коммит, уже импортированный остановленный web-образ
и подготовленная конфигурация четырёх WAN и двух overlay-туннелей SiteA.
Подготовка выполняется существующей утилитой:

```bash
python3 tools/overlay_container.py prepare --project-root /path/to/private/project
```

Проверьте, что уже нет запущенного прогона:

```bash
python3 tools/network_soak.py status --lab-root /path/to/private/project
```

Короткая проверка самого драйвера использует отдельный отчёт и **не является
приёмкой длительного прогона**:

```bash
python3 tools/network_soak.py run --lab-root /path/to/private/project --smoke-seconds 180 --sample-seconds 10
```

Основной прогон — 48 часов: первые 24 часа та же конфигурация работает на тёплом
RouterOS fallback, затем включается локальный контейнер без повторной установки
правил. До начала измерения все четыре WAN должны удерживать здоровый SLA
60 секунд подряд в пределах отдельного 240-секундного прогрева. Общее время
измерения можно увеличить до 72 часов. Запускайте единственный процесс
в устойчивой фоновой сессии и сохраняйте его PID:

```bash
python3 -u tools/network_soak.py run --lab-root /path/to/private/project --hours 48 --native-hours 24
```

Три исходные TCP-сессии постоянно передают данные: обычный интернет, выбранный
по Address List VPN-WAN и частный межфилиальный маршрут. Драйвер проверяет
сохранение исходных и ответных TCP/NAT-кортежей, рост счётчиков и единственный
активный HTTP-запрос без переподключения. API `.id` может измениться при живом
потоке; такие изменения регистрируются отдельно. Проверяются выбор приоритетных
WAN, SLA выбранных каналов, наличие отчётов всех четырёх WAN SiteA, восемь
OSPF-соседств, свежесть контроллеров и неизменность
исходников, установленных библиотек, активных конфигураций и файла intent
внутри каждой фазы. При старте контейнера ожидается одноразовая заявка владения;
её изменение записывается отдельно, затем фиксируется новая база intent.
Начальные операции подготовки стенда и финальное восстановление меняют его
конфигурацию; периодические измерения выполняют только чтение API.

Изменения SLA невыбранных резервов сохраняются в статистике качества и событиях.
Краткое ухудшение резервного канала само по себе не означает отказ контроллера.
Для выбранных WAN1/VPN1, частных путей и трёх непрерывных потоков условия остаются
строгими. Порог SLA продукта и профиля стенда драйвер не меняет.

При включённом контейнере дополнительно проверяются аутентифицированный web,
ограничение истории 12 точками, точный image ID и RSS. Бюджет RSS стенда по
умолчанию 32 MiB (`--max-rss-mib`); это условие приёмки, а не обещание расхода
памяти на физических ARM/LTE. Счётчики записи процесса проверяются только когда
ядро их предоставляет. Недоступные счётчики остаются неизвестными. Стабильный
intent не доказывает отсутствие любых аппаратных записей флеша RouterOS.

Отчёт `runtime/overlay-lab/runtime/network-soak.json` и последовательные JSONL
измерения находятся в приватном проекте на хосте. Время считается по монотонным
часам фактически работающего драйвера. Возраст виртуальной машины и старые
отчёты не засчитываются. Любая ошибка оставляет `pass: false`; успешным прогон
становится лишь после полного времени обеих фаз и успешного восстановления
исходной конфигурации. Для короткой проверки используются имена `network-soak-smoke*`.

SIGINT/SIGTERM останавливают контейнер, убирают временный трафик/правила и
возвращают исходную конфигурацию. Перед этим она сохраняется на хосте в приватном
`network-soak-before.json`. После аварийного завершения или выключения хоста
сначала проверьте PID, блокировки и остатки временных объектов; не запускайте
второй прогон поверх незавершённого восстановления. Владелец может остановить
работу в любой момент. Во время прогона нельзя менять проверяемый Git-набор
или запускать другие тесты с изменениями на этом стенде.

Точный image ID, коммит, длительность, количество измерений, диапазон RSS и
известность I/O-счётчиков сохраняются в отчёте. До фактического завершения этих
48–72 часов длительная проверка остаётся незавершённой и выпуск не публикуется.
