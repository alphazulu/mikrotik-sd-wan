# Нагрузка и запись на hAP ax2: 0.4.0

Русский | [English](HAP-AX2-04-PERFORMANCE.en.md)

13 ноября 2026 завершено первоначальное сравнение baseline, RouterOS RSC и
локального ARM64 base-контейнера 0.4.0 на выделенном hAP ax2 с RouterOS 7.25.1.
Из **27 интервалов 19 пригодны для сравнения устойчивого пути**, восемь UDP-интервалов
сохраняются как отрицательный результат нагрузки. Вся серия не объявляется PASS.
Исходная конфигурация и файлы восстановлены; временный стенд удалён.
[Функциональная приёмка и точные исходники/образ](HAP-AX2-04-VALIDATION.md).

## Метод

Один физический аплинк; два виртуальных WAN и LAN через локальный компьютер
в том же коммутаторе. Использованы Linux namespaces, WireGuard MTU 1200 и
VXLAN с внутренним MTU 1140; MTU WSL 1280. Генераторы и приёмники трафика
находились за MikroTik. CPU включает обработку этих туннелей.

Для каждого режима: 60 секунд установления состояния, 120 секунд без клиентской
нагрузки и 45 секунд контроля отложенной записи, TCP в обоих направлениях по
два повтора 20 секунд с четырьмя потоками, затем UDP с payload 1000 байт также
в обоих направлениях по два повтора. Предложенная UDP-нагрузка — 85% меньшего
из двух TCP-результатов baseline **в соответствующем направлении**: около
187,16 Мбит/с вверх и 180,30 Мбит/с вниз.

Наблюдатель использовал одну постоянную API-сессию без переподключений в
измеряемых интервалах. Ресурсы опрашивались каждые две секунды, SD-WAN status —
каждые шесть. Для трафика CPU считается только в интервале работы генератора.
Результат приёмника сверялся отдельно от стабильности выбора WAN.

## Без клиентской нагрузки

| Режим | Средняя загрузка CPU роутера | Прирост записанных секторов за 120 + 45 секунд | Пиковая memory-current контейнера |
|---|---:|---:|---:|
| Baseline | 0,02% | 0 | — |
| Нативный RSC | 14,17% | 0 | — |
| Локальный Rust base | 15,93% | 0 | 544 768 байт, около 0,52 MiB |

Это общая загрузка CPU MikroTik с действующими SLA и измерителем. memory-current
— показатель cgroup контейнера в этом интервале, а не вся память RouterOS или
стоимость SD-WAN вместе с нативными скриптами и Netwatch. Web-профиль здесь не
измерялся. Нулевой прирост относится к этим ограниченным интервалам.

## TCP: среднее двух повторов

Вверх означает клиент → приёмник за WAN; вниз — обратное направление.
Все 12 TCP-интервалов имели устойчивый выбор WAN и пригодные измерения.

| Режим | Приёмник вверх, Мбит/с | Приёмник вниз, Мбит/с | CPU вверх | CPU вниз |
|---|---:|---:|---:|---:|
| Baseline | 221,15 | 213,24 | 69,50% | 71,55% |
| Нативный RSC | 176,65 | 179,48 | 81,60% | 79,50% |
| Локальный Rust base | 170,77 | 173,43 | 84,15% | 80,30% |

В каждом режиме хотя бы одно ядро достигало 100%. В этих TCP-интервалах
прироста счётчика записи не наблюдалось. Разница относится ко всей проверенной
схеме с туннелями, правилами, SLA и контейнером. Это не максимальная скорость
обычной Ethernet-маршрутизации hAP ax2 и не сравнение ускорения с версией 0.3.
Двух коротких повторов недостаточно для универсальных аппаратных рекомендаций.

## Отрицательные UDP-интервалы

Четыре UDP-интервала baseline пригодны для измерения. Все восемь UDP-интервалов
native/container исключены из сравнения устойчивого пути: во время нагрузки
менялся выбор WAN, в том числе закрывались оба пути по SLA. В первых native
интервалах вверх потери составили примерно 52,72% и 69,92%; в последующих
интервалах вниз приёмник завершался по таймауту. Успешное завершение генератора
само по себе не доказывает исправность пути.

В исходной методике не было отдельного ожидания здоровых SLA перед каждым
UDP-интервалом. Поэтому поздние интервалы могли начаться во время восстановления
после предыдущего отказа. Они описывают последовательность нагрузочного стресса,
а не восемь независимых устойчивых сравнений. Для уточнения нужен меньший общий
поток и явный барьер здоровья перед каждым интервалом; эта серия не заменяется
задним числом удачными попытками.

При этих переходах наблюдались записи: native 14/15/4/12 секторов, container
21/13/8/12. Их нельзя приписывать idle-опросу RAM-inbox: интервалы содержали
смену состояния и маршрутов. Счётчик секторов не измеряет erase-циклы flash и
не определяет срок службы носителя. [Что продолжает записываться](RAM-CONTROL.md).
