## Измерение API и места

На каталоге из 2316 файлов медиана трёх чтений полного списка `.id,name` была
1,926 с. Чтение небольшого journal pointer новым точечным запросом вместе с
получением содержимого занимало 0,04054 с: около 47 раз меньше в этом опыте.
Это лабораторный замер API, не обещание ускорения всех операций на любом железе.

Подготовка подтверждённой установки заняла 6,3 с; в ранее измеренном длительно
работавшем стенде до оптимизации —65,77 с. Измерения сделаны в разные моменты
одного стенда, поэтому их нельзя считать строгим CPU-бенчмарком. Прежние полные
запросы каталога заменены ограниченными запросами к нужным именам.

На настоящем каталоге CHR безопасная очистка удалила 2338 устаревших файлов,
34895269 байт логических данных, за 195 с. Свободное место изменилось с 430567424
до 471658496 байт (примерно+39,2 МиБ с учётом файловых блоков/метаданных).
Active JSON, controller source и текущая транзакция остались прежними.
Это разовая очистка накопленной истории, не фоновая операция каждого цикла.

Установка с `maintenance.backup_keep=3` вызвала очистку ровно один раз после
committed и удалила 13 файлов прежней группы. Затем применён исходный JSON без
maintenance: все SLA healthy, default/client101→WAN1, client102→WAN2,
strict103→WAN3. Оба стенда оставлены работающими, контейнер активен.

## Достоверность отказов

Старый сценарий API-disable мог завершиться ошибкой выбора динамической
service-записи до фактического отключения API. Fixture исправлен: выбирается
единственный static service, проверяется `disabled=true`, затем вызывается
явная ошибка. Journal обязан содержать именно эту причину перед утверждением
об успешном восстановлении. Сценарий повторно прошёл на CHR.

Повреждённый journal, пустая/неверная текущая схема, несоответствие identity,
pending/recovery и смена ID файла не приводят к удалению. Неудачная подготовка
без готового binary backup не вытесняет сохранённые рабочие точки восстановления.
Неожиданная ошибка обслуживания после committed не выдаётся за провал установки.

## CI и пределы

На этом этапе workflow запускал Python на Linux/Windows, GUI offline в Windows, Gitleaks,
Rust unit9 и cross-build/ELF/archive checks трёх архитектур. CI не подключается
к MikroTik и не запускает CHR fault tests. Release job с write-правами работает
только на явно отправленном теге `v*` после остальных jobs; обычные jobs read-only.
Скачанные CI archives проверены по опубликованному в artifact `SHA256SUMS`.

Наличие compiler build paths означает, что побитовое совпадение CI ELF с
исходным локальным v0.1.0 не заявляется. Код контроллера остаётся тем же;
размеры и hashes каждого build записываются в его build-report.

Полные локальные отчёты хранятся в исключённом из Git `runtime/`. В публичный
репозиторий не входят passwords, device exports, journals/backups и private
inventory. Защита публикации и secret scanning остаются обязательными.
