# LTE WAN через существующий APN

Русский | [English](LTE.en.md)

Поддержка native LTE добавлена в RouterOS-контроллер, установщик и GUI. Прежняя приёмка: 109 unit и 105 проверок CHR, Windows GUI и аудит стенда. [Результаты и пределы проверки](LTE-VALIDATION.md). Для каждого WAN используется один routed IPv4 APN. У RNDIS/HiLink RouterOS дополнительно создаёт внутренний динамический DHCP-клиент; SD-WAN читает его шлюз, а настройками automatic default продолжает управлять через APN.

## Настройка в GUI

1. Откройте `Configure-SD-WAN.cmd`, подключитесь к API и получите настройки.
2. Отметьте основной интерфейс и LTE-интерфейс. Например, `wan-primary` с приоритетом 1 и `lte-backup` с приоритетом 2.
3. Мастер показывает тип LTE, назначенный APN-профиль и текущий IP. APN и runtime адреса в мастере доступны для просмотра; изменение профиля оператора выполняется штатными средствами RouterOS. В редакторе WAN указывается имя уже назначенного профиля, чтобы обнаруживать его последующую замену.
4. Задайте контрольные цели, SLA и политики клиентов. Посмотрите план: установка сохранит исходный APN routing flag и отключит его automatic default для управления маршрутами по SLA.
5. Примените через защищённую установку. Стандартный пакет содержит JSON и 11 RSC. После установки внешний GUI не нужен.

Настроенные LTE interface/APN и необходимый NAT должны существовать заранее. Конфигуратор не создаёт профиль с учётными данными, не меняет PIN, SIM, оператора, режим радиосети или credentials. Временно отсутствующая data session допускается: WAN остаётся unavailable, пока не появятся IPv4 и свежие измерения.

**DNS перед установкой.** На RouterOS 7.24.5 попытка отключить APN automatic default при `use-peer-dns=yes` возвращает `Can't use DNS without route!`. Сначала настройте явные DNS-серверы маршрутизатора и отключите `use-peer-dns` у выбранного APN штатными средствами RouterOS, затем повторно получите настройки. Конфигуратор и native installer проверяют это до adoption. Они не отключают DNS молча и не копируют динамические DNS в постоянную конфигурацию. Непрочитанное состояние этого флага также блокирует установку.

**Существующие OSPF/VPN-политики требуют отдельной миграции.** Guard сторонних connection/routing marks сохраняется. Поддержка LTE не отменяет проверку совместимости: [OSPF/VPN](OSPF.md).

## Поля JSON

У LTE WAN обычные параметры имени, probe_table, icmp_target и probes. Дополнительные поля адресации:

```json
{
  "kind": "lte",
  "interface": "lte1",
  "apn_profile": "default"
}
```

Это фрагмент существующего WAN, а не полный файл конфигурации. `address` и `gateway` отсутствуют: снимок LTE IP валидатор отвергает. `apn_profile` — имя профиля, а не строка APN оператора и не пароль. Профиль должен совпадать с назначенным интерфейсу.

## Маршруты и переподключение

- Источник — назначенный динамический IPv4; next hop у raw-IP LTE — LTE interface. Для RNDIS/HiLink используется текущий шлюз внутренней bound DHCP lease, закреплённый как `IP%interface@main`. Пробы и ответы закреплены за таблицей соответствующего WAN. При отсутствии или неоднозначности lease шлюз не угадывается и WAN закрывается.

  Это соответствует [ограничению interface gateway в RouterOS](https://help.mikrotik.com/docs/spaces/ROS/pages/328084/IP+Routing): в broadcast-сети такой маршрут отправляет ARP к самому адресу назначения и пригоден только для непосредственно подключённых адресов. Свойства APN описаны в [LTE/5G](https://manual.mikrotik.com/docs/mobile-networking/lte-5g/). Ошибка сочетания peer DNS и отключённого automatic default выше подтверждена отдельной проверкой на 7.24.5 x86.
- APN `add-default-route` выключается, чтобы автоматический маршрут не обходил SLA через main. Приоритеты SD-WAN задаются порядком WAN в политиках, а не переписыванием APN distance.
- Installer сохраняет APN baseline до изменения. Если automatic default уже выключен, лишний setter не выполняется. Повторная установка сохраняет первоначальную запись, а не принимает управляемое значение за исходное.
- При disconnect/new-IP меняются source bindings и маршруты, затронутые сессии удаляются, затем контроллер ждёт нового поколения probes, recover и hold-down. Сессии других политик и входящий API через исправный WAN сохраняются.
- Неожиданная смена APN или возврат automatic default делают LTE unavailable. Контроллер не начинает изменять другой профиль без новой согласованной установки.
- LTE остаётся резервным, если стоит после основного WAN в prefer политике. Для конкретного клиента можно задать собственный порядок либо strict LTE.

Distance скрыт RouterOS при выключенном automatic default, включая native get, но сохранён внутри профиля. Код не записывает distance обратно. На CHR проверено 77→no→yes→77.

## Общий профиль и откат

Если один APN используется несколькими выбранными LTE-интерфейсами, baseline хранится один раз. Если его использует невыбранный модем, установка отклоняется, включая случай отключённого модема: изменение общего профиля затронуло бы чужой WAN. Используйте отдельный APN-профиль или включите все его интерфейсы в согласованную конфигурацию.

Baseline rollback восстанавливает только изменённый routing flag при совпадении APN identity и управляемого значения. Ручные изменения и новый неуправляемый пользователь общего профиля не затираются. Retired profiles остаются без automatic default до явного baseline rollback. Аварийный worker/watchdog возвращает полный зашифрованный binary backup и прежние файлы с перезагрузкой, включая APN configuration.

## Границы поддержки

- Native LTE routed IPv4 и один APN на логический LTE interface. Multi-APN на одном старом интерфейсе и passthrough отвергаются, чтобы не выбирать произвольный source из нескольких сессий.
- Внешний LTE-модем, подключённый обычным Ethernet-интерфейсом, настраивается как DHCP WAN. USB RNDIS, отображаемый RouterOS в `/interface/lte`, остаётся LTE WAN; его внутренний динамический DHCP-клиент не редактируется. Пользовательский статический DHCP-клиент на том же LTE-интерфейсе считается конфликтом.
- Входящие соединения возможны только при фактической достижимости адреса провайдером. SD-WAN не устраняет CGNAT и не открывает firewall порты.
- Переключение Internet WAN не переносит GRE/IPIP/EoIP с фиксированным IP основного провайдера на LTE. Резерв межфилиальных туннелей требует согласованной overlay схемы.

В первоначальной CHR-матрице проверялись реальное APN menu и настоящий data plane, при этом сведения о физическом LTE-устройстве в тестовом пакете заменялись адаптером над PPP point-to-point. Позже отдельно проверен USB RNDIS на x86. Это не проверка SIM, радиорегистрации, прошивки или конкретного физического модема. В production пакете нет test-mode. Актуальное состояние кандидата — [CURRENT-STATUS.md](CURRENT-STATUS.md).
