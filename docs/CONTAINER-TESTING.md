# Обязательное unit-покрытие контейнера

При каждом изменении контейнера проверяются оба Rust-профиля (`base` и `web`),
основной цикл `main.rs`, все библиотечные модули и браузерный JavaScript.
Требование владельца закреплено в [правилах контейнера](../container-controller/AGENTS.md).

На Linux amd64 / WSL с установленным Rust SDK проекта:

```bash
python3 tools/install_container_test_tools.py
python3 tools/container_checks.py
```

Проверка требует **100% исполняемых строк и функций каждого рабочего файла**.
Из расчёта исключаются только исходники тестов. Ветвления выводятся отдельно;
покрытие не заменяет проверки ожидаемого результата и обработку ошибок.
Инструменты покрытия устанавливаются только на машине сборки, в scratch-образ
они не попадают. Cargo LLVM Coverage закреплён на0.9.1, архив проверяется SHA256.

JSON-отчёты, журналы и результат лежат в `runtime/container-unit/` и не публикуются
в исходниках. `--output` или `SDWAN_CONTAINER_COVERAGE` позволяют выбрать другой
каталог. `SDWAN_LLVM_COV` задаёт путь к установленному cargo-llvm-cov той же версии.
Используйте `CARGO_HOME`/`RUSTUP_HOME` своего SDK, если он расположен вне проекта.

Штатная сборка `python3 container-controller/build.py` проверяет успешный результат
покрытия, привязанный SHA256 ко всем текущим файлам контейнера и инструментам
проверки. При изменении исходников или тестов старый результат перестаёт подходить,
и проверка выполняется заново. Пропуска проверки в утилите нет. SHA256 проверенного
набора сохраняется в отчёте каждого образа.

CI запускает такую же проверку перед сборкой шести scratch-образов. Отчёты CI
сохраняются отдельным артефактом, в том числе при ошибке. При изменении поведения
после unit-проверки дополнительно выполняется приёмка конкретного образа на CHR.
Рабочий MikroTik для этих проверок не используется.

Текущий проверенный набор: 41 тест базового Rust-профиля, 75 тестов профиля web
и 8 тестов JavaScript. Все рабочие файлы проходят порог строк и функций.
В частности, тесты проверяют несовпадение конфигурационной эпохи до heartbeat,
каждый этап освобождения ресурсов при старте веб-сервера, ограниченные JSON-
декодеры, ошибки записи HTTP-заголовков и продолжение работы после неверных
запросов. Порог относится к строкам и функциям: 100% покрытия ветвей из него
не следует; ветви JavaScript измеряются отдельно, а stable LLVM не выводит
полную метрику ветвей Rust в используемом режиме.

Проверки браузера также воспроизводят потерю HTTP после свежего снимка,
пометку прежних WAN/VPN/overlay как устаревших, восстановление и очистку при
выходе. Offline Chromium fixture запускается отдельно от unit-покрытия:

```bash
python3 tests/browser_network_smoke.py --chrome /path/to/chromium --output /path/to/new/report-directory
```

На хосте нужны Playwright и Chromium; в контейнер они не устанавливаются.
Fixture сохраняет CSP рабочего сервера и использует синтетические данные.
Проверка настоящего API и импорт конкретного образа на CHR выполняются отдельно.

## Нативная проверка приоритетов intent

Rust-покрытие не заменяет проверку адаптера RouterOS. На уже подготовленном
изолированном LTE-стенде выполняется:

```bash
python3 tests/container_priority_acceptance.py --lab-root /path/to/SD-WAN
```

Нужен Git checkout с историческим коммитом `1b2a9d6`: из него берётся прежний
адаптер для воспроизведения регрессии. Драйвер проверяет фиксированные loopback
QMP/API и имена собственных CHR/x86, занимает блокировку стенда и отказывается
использовать узлы с работающим SD-WAN. Он исполняет неизменённые фрагменты
нативного выбора и сгенерированной проверки intent в самом RouterOS.
Маршруты, firewall и scheduler не меняются; это проверяется сравнением снимков.
Два временных файла удаляются после проверки.

В матрице 20 случаев на каждом устройстве: возврат на приоритетный канал,
устаревший `none`, недоступный основной, допустимый degraded, healthy перед
degraded, drain/down, strict и обратный порядок приоритетов. Прежний код
нарушает ожидаемое поведение в 7 случаях на каждом устройстве; исправленный
проходит все 20 на CHR и все 20 на x86 RouterOS 7.24.5. Отдельная полная
приёмка и короткий forced smoke проверяют применение этих решений к реальным
маршрутам, TCP/NAT и сохранению незатронутых соединений.
