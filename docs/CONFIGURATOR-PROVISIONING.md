# Подготовка устройства и выбор локального контроллера

Ветка разработки 0.3.0. Решения SD-WAN по-прежнему выполняются внутри MikroTik:
RSC либо локальный Rust-контейнер scratch. Конфигуратор нужен для подготовки.

## Проверка платформы

После подключения читаются модель/архитектура, CPU и число ядер, RAM, накопители,
пакеты и ограничения device-mode. Пароли, ключи и серийные номера для этой проверки
не запрашиваются. Недоступное поле помечается неизвестным, а не успешным.

Рекомендация режима использует `config/platform-benchmarks.json`. Запись должна
содержать успешный отчёт с SHA256, совпадающие модель/CPU/RAM/версию RouterOS,
привязку к исходникам контроллера, условия трафика и не меньшую конфигурацию
WAN/политик/проб/туннелей. Сейчас полных сравнительных профилей нет: конфигуратор
честно показывает «нет подходящих замеров». RSC предлагается как начальный вариант,
без обещания производительности. Режим можно выбрать вручную.

Функциональный тест LTE и короткий soak не подменяют измерение пропускной способности.
Результат QEMU не переносится на физический ARM/ARM64 по одному имени архитектуры.

## Подготовка пакетов и функций

На вкладке «Контроллер»:

1. «Проверить готовность» показывает пакеты, разрешения, свободную RAM и носитель.
2. «Подготовить пакеты и функции» при необходимости скачивает официальный пакет
   `container` точно для RouterOS 7.24.5 и архитектуры устройства, передаёт его с
   проверкой SHA256 и выполняет штатную перезагрузку с повторной проверкой личности
   устройства и активной версии пакета.
3. Изменяются только требуемые флаги device-mode: scheduler/fetch, container для
   контейнерного режима и l2tp при соответствующем WAN. Traffic generator,
   bandwidth test и остальные необязательные функции автоматически не включаются.
4. Если Fetch запрещён, сначала запрашивается разрешение функции, до передачи
   пакета. Device-mode требует физического подтверждения кнопкой reset/mode либо
   отключением питания; обычный reboot его не заменяет. Подробности выводятся в
   журнал до ожидания API. После подтверждения нажать проверку повторно.

Запрос device-mode фиксируется локально **до** отправки. При обрыве API программа
не объявляет функцию включённой и не повторяет запрос вслепую: повторный update
может отменить уже ожидающее подтверждение изменение. Готовность устанавливается
по фактически прочитанным флагам. Роутеры с flagged=yes не «исправляются» автоматически.

## Накопитель и образ

Предлагаются доступные внешние ext4/btrfs-носители и внутренний persistent-каталог
(включая flash/ там, где остальной корень — RAM). Видны доступность и свободное
место. Резерв 16 MiB — запас для установки, **не** оценка производительности.
Носители не форматируются; swap и запись статистики на flash не включаются.

«Подготовить контейнер» выбирает base/web и amd64/armv5/arm64 по архитектуре и
настройке веб-статистики. Образы привязаны к `config/container-images.json`:
архив SHA256, размер, image ID и digest покрытия точного исходного кода.
Используется проверенный локальный архив из dist/container, иначе загрузка по
фиксированному HTTPS URL релиза. **Релиз 0.3.0 пока не опубликован**: до публикации
автоматическая загрузка из GitHub может вернуть 404; молчаливой замены образом
0.2.0 или случайным latest нет. В выполненном тесте использовались точные CI-архивы.

Передача использует Fetch и временный HTTP endpoint конфигуратора: один архив,
случайный URL, ограниченный адрес отправителя, без выдачи каталогов. После передачи
файл читается по native API кусками и SHA256 сравнивается побайтово; UTF-8 не
применяется к бинарным данным. Нужен доступ от MikroTik к компьютеру; при его
отсутствии возможна прямая HTTPS-загрузка того же закреплённого публичного образа.
Для такой проверки используется подключение api:// или apis://. Файл с другим
содержимым на выбранном пути не перезаписывается.

SDK создаёт отдельную локальную сеть, API-пользователя, read-only mounts и лимит
памяти. Импортированный image ID сверяется с закреплённым CI-образом. Подготовленный
контейнер остановлен: маршрутизация применяется отдельной защищённой установкой.
Совпадающий уже работающий контейнер не перезаписывается. Смена его образа требует
управляемого обновления остановленного экземпляра, а не незаметной замены filesystem.

## Проверено на стенде

- Windows Tk GUI: аппаратный опрос, видимость отсутствующего пакета/флага,
  ручной выбор режима, смена base/web образа и каталога.
- x86 7.24.5 L6: 128 KiB binary roundtrip с SHA256 и повторная передача без записи;
  установка официального container NPK, штатный reboot, физическое подтверждение
  через cold boot отдельной VM; L6 сохранена.
- Автоматическая передача/импорт точного scratch CI-образа; локальная сеть, пользователь,
  mounts и остановленное состояние проверены SDK check_ready.
- Покрытие Rust base/web и браузерного JS повторно измерено: 100% исполняемых строк
  и функций; метрики ветвей сохранены отдельно. Runtime-source digest прежний.

Рабочий MikroTik не изменялся. Запуск SD-WAN с настоящим LTE в новой x86-топологии,
сравнительный нагрузочный тест и новый 48-часовой soak ещё предстоят.
