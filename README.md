# MikroTik SD-WAN

Русский | [English](README.en.md)

SD-WAN для RouterOS: контроль SLA, приоритеты каналов, автоматическое переключение
и политики клиентов. Контроллер работает на самом MikroTik — как скрипты RouterOS
либо один статический процесс Rust в образе `FROM scratch`. Внешний сервер для
маршрутизации не нужен. Конфигуратор используется при настройке и диагностике;
после установки его можно закрыть.

## Состояние проекта

В этой ветке развивается кандидат **0.3.0**. Web-интерфейс, VPN WAN и филиальный
overlay реализованы и прошли целевые проверки. Длительная приёмка текущего
кандидата продолжается; выпуск 0.3.0 ещё не опубликован. Каталог образов содержит
его будущие URL: до выпуска автоматическая загрузка может вернуть HTTP 404.

[Текущее состояние проверок](docs/CURRENT-STATUS.md) отделено от исторических
отчётов и [плана развития](ROADMAP.md). Прохождение короткой проверки не означает
завершения длительного прогона или подтверждения аппаратной производительности.

## Возможности

- IPv4 WAN: статические интерфейсы, DHCP-client, PPPoE, LTE с существующим APN и
  уже настроенные WireGuard, L2TP, SSTP и OpenVPN-клиенты.
- SLA по доступности, RTT, джиттеру и потерям: независимые цели, кворум, окна
  отказа и восстановления, задержка возврата и контроль свежести измерений.
- Единые очереди WAN, включая VPN. Источник и назначение политики — IP/подсеть
  или Address List MikroTik; условия можно сочетать. Поддерживаются интерфейс,
  протокол, порты, приоритет правил и режимы `prefer`/`strict`.
- Маркировка соединений и таблицы маршрутизации для симметричных WAN/DNAT-ответов.
  При переключении удаляются соответствующие управляемые записи conntrack.
- Режимы обслуживания `enabled`, `drain`, `down` и отдельные цепочки `jump`.
- Опциональные филиальные WireGuard/OSPF-пути через доступный публичный хаб,
  в том числе для филиалов за CGNAT; внутренние SLA-пробы и защита локальных сетей.
- GUI/CLI, редактируемый JSON, предварительный план, диагностика и объяснение
  выбора канала. Существующие настройки провайдера и VPN задаются заранее.
- Защищённая установка: локальные worker/watchdog, зашифрованный backup и
  подтверждение через новое API-соединение. При потере контейнера работает RSC.
- Опциональный web-образ: история SLA/RX/TX, политики и события в RAM, экспорт
  JSON на компьютер. Модуль выключен по умолчанию и не изменяет настройки.
- Минимизация повторных файловых записей и явная политика хранения архивов.

## Поддерживаемая среда

Установка закреплена на **RouterOS 7.24.5**. GUI/CLI проверены с **Python 3.12**;
зависимостей pip нет, для GUI нужен Tkinter. Образы Rust собираются для
`linux/amd64`, `linux/arm64` и `linux/arm/v5`; выполнение проверено на CHR/x86.
Сборка для ARM сама по себе не подтверждает работу и производительность на
физическом устройстве. Для контейнерного режима нужны подходящие пакет,
архитектура, device-mode и носитель: [подготовка устройства](docs/CONFIGURATOR-PROVISIONING.md).

Лаборатория работает на Linux/WSL2 с QEMU. Диски, порты и ресурсы разных топологий
учитываются отдельно; нагрузочные воздействия выполняются последовательно.
Подробности — [лаборатория](docs/LAB.md) и [внешние генераторы](labtools/README.md).

## Быстрый старт

```sh
git clone https://github.com/alphazulu/mikrotik-sd-wan.git
cd mikrotik-sd-wan
python3 configurator.py
```

В Windows также доступен [Configure-SD-WAN.cmd](Configure-SD-WAN.cmd).

1. Подключитесь к API и прочитайте настройки. Для TLS используйте `apis://` с
   проверяемым сертификатом; обычный API — в доверенной сети управления.
2. Отметьте WAN и задайте приоритеты. Для PPPoE нужен логический PPPoE client;
   для LTE — интерфейс и существующий APN. VPN добавляется как обычный WAN.
3. Настройте контрольные цели, SLA, внутренние сети и политики; сохраните JSON.
4. Выберите RSC или локальный контейнер. Для контейнера проверьте предпосылки,
   выберите носитель и отдельно подготовьте подходящий образ.
5. Прочитайте план изменений и выполните защищённую установку. Проверьте
   подтверждение и диагностику через новое соединение API.

Работа со сторонними mangle начинается с [плана миграции](docs/MIGRATION.md),
а не с массового отключения правил. Создание черновика не разрешает его установку.

## CLI и конфигурация

В репозитории только синтетические примеры. `config/sdwan.json` содержит настройки
лаборатории; для своего устройства создайте JSON через мастер. Исторический
`config/sdwan-intent.json` не является входным файлом установщика.

```sh
python3 sdwan.py --config config/sdwan.json validate
python3 sdwan.py --config config/sdwan.json bundle --output build/native
```

Учётные данные хранятся в отдельном локальном файле вне Git. Команды `plan`,
`apply`, `status`, `events` и `rollback` используют параметры подключения,
CA, credentials и ожидаемую identity устройства. Пошаговые примеры:
[конфигуратор](docs/CONFIGURATOR-WIZARD.md), [JSON](docs/CONFIGURATION.md),
[установка и откат](docs/DEPLOYMENT.md), [хранение секретов](SECURITY.md).

## Контейнер и web

В scratch-образе один Rust/musl ELF с UID `65532:65532`; нет shell, дистрибутива
или БД. Настройки и секреты подключаются отдельными mounts только для чтения.
Два профиля (`base`, `web`) и три архитектуры дают шесть архивов. Точные размеры,
SHA256 и image ID указаны в [каталоге](config/container-images.json) и build report;
локальная сборка может отличаться от CI побайтово.

Перед каждой сборкой после изменения контейнера обязательны **100% исполняемых
строк и функций** Rust base/web, `main` и браузерного JavaScript. Покрытие связано
с точными исходниками; ветви учитываются отдельно. Новый образ также проверяется
на изолированном RouterOS. См. [покрытие](docs/CONTAINER-TESTING.md),
[сборку](docs/BUILD.md), [установку](docs/CONTAINER.md) и [web](docs/STATISTICS.md).

Статистика хранится в RAM. Перезагрузка, смена конфигурации или замена контейнера
очищают историю. Неизвестные счётчики записи не интерпретируются как ноль.
Измерения виртуального стенда не превращаются автоматически в рекомендации
для физических ARM/ARM64: [методика](docs/PERFORMANCE-PLAN.md),
[исторические результаты](docs/PERFORMANCE-RESULTS.md).

## Проверки и границы

```sh
python3 -m unittest discover -s tests -p 'test_*.py'
python3 tools/audit_public_tree.py
python3 tools/container_checks.py
```

Последняя команда требует SDK из [инструкции по покрытию](docs/CONTAINER-TESTING.md).
Не запускайте второй прогон или воздействие на занятый стенд. Текущие и
исторические результаты не суммируются как число уникальных тестов.

Поддерживается IPv4. IPv6, PCC/взвешенная балансировка, QoS и классификация
приложений сверх L3/L4 остаются в плане. Существующие OSPF/VPN, VRF и чужие
маркировки требуют согласования; универсальная миграция не реализована.
CGNAT не обеспечивает входящую доступность сам по себе.
